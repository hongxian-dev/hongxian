## 0. 这份文档要解决什么

C2 是「三条防护」的代码任务，但开发卡在措辞上。三段话面向用户，写歪了不是"不够好看"，而是**把不该承诺的事承诺出去**——一旦出事，虚假的安全承诺会成为最大的反噬点。

所以本文的判据不是"文案好不好"，而是：**每一句都必须是平台真能做到的事**。做不到的，宁可写"我们做不到"。

三条防护对应三个不同的失效场景：

| 防护 | 防的是什么 | 触发时机 |
|---|---|---|
| 一 · 风险提示 | 用户完全不知道规则就开始用，被骗后说"平台什么都没说" | 首次使用、建画像之前 |
| 二 · 举报即断 | 举报了但对方还能继续投递，用户继续受伤害 | 举报动作发生时，立即生效 |
| 三 · 披露声明 | 用户以为"平台什么都不知道"，实际上贴卡后平台能关联到邮箱 | 贴广场之前 |

---

## 1. 五条共同原则

1. **不承诺能力之外的保护。** 平台看不见内容、不能核验身份、不能追回资金。这三件事都不写进"我们会保护你"。
2. **不留兜底条款。** 不写"一般情况下""除特殊情况外"——这等于什么都没说。
3. **具体到"什么时候、会发生什么、你该做什么"。** 反诈信息之所以无效，多数是因为只讲原则不讲动作。
4. **不做道德劝说。** 不说"要提高警惕""要理性判断"——用户被骗不是不够理性，是对方太专业。
5. **承认边界。** 技术上做不到的（如"绝对不可关联"），明说做不到。

## 2. 防护一 · 首次使用风险提示

### 2.1 触发与形态

| 项 | 规格 |
|---|---|
| 触发点 | 首次调用 `build_profile`（建画像）之前。此时用户还没有产生任何数据 |
| 形态 | MCP 工具返回的**阻塞式确认块**，纯文本（宿主 UI 差异大，不依赖图形组件） |
| 阻塞规则 | 未确认不得进入建画像。`build_profile` 返回 `ACK_REQUIRED` + 全文 + 一行确认指令（可继续的中间态，不是报错） |
| 确认记录 | 写入本地 `~/.hongxian/ack.json`：`{ "version": "1.0", "at": "..." }`，**不上报、不联网** |
| 重复展示 | 文案版本号 +1 时重新展示。版本号不变则永不重复 |
| 为什么不上报 | 零知识原则。平台连"多少人看过"都不该知道，除非用户 opt-in 计数 |

> 不做默认勾选。勾选框默认必须是空的。

### 2.2 文案（建议稿，可直接落地）

```
红线是工具，不是婚介，也不是担保。

我们给你一套自己用的工具：建画像、换名片、比一比、出报告。
决定见不见的是你，心动归你。这句话不只是说法，是架构——
画像、报告、对话都只存在你自己的设备上，服务器只是个信箱。

三件事得说明白。

一 · 我们不知道对面是谁
没有实名、没有身份核验、没有背景调查。对方说的话，我们既无法
证实，也无法否证。"聊了三个月"、"见过父母"、"他朋友圈很真实"
——都不是证据。我们不替任何人背书。这条不能替，也不敢替。

二 · 钱一出现，就是警报
在现实里核实过对方身份之前，任何人以任何理由要你转账、投资、
代付、刷单、"先帮我垫一下"、"有内部渠道"、"家里急用"、
"证明你是真心的"——都是诈骗。没有例外，真的没有例外。
骗子不会因为你的情况特殊就变成真的。

三 · 有人会冒充我们
我们不会在任何对话、任何工具、任何卡片里向你索要钱、索要验证码、
索要私钥或 24 词恢复短语，也不会让你下载别的东西来"配合验证"。
赞助入口只在我们网站的页脚，永远自愿，与能不能匹配毫无关系。
任何人自称"红线工作人员"要你做上面任何一件事，都是假的。

出事了怎么办：
· 钱已经转出去 —— 立刻打 110 或 96110（反诈专线）。不要先来找我们，
  我们追不回资金，只有警察能冻结。
· 人身安全受威胁 —— 先离开现场，再报警。
· 在工具里用 report_abuse 举报，我们会立刻切断他向你投递的通道。

你随时可以退出。一条命令删净本地数据；服务器上的信箱也能即刻清空。

[ ] 我读完了，并且明白平台不为对方的身份做任何担保
```

### 2.3 关键取舍

- **第一句定生死。** "工具，不是婚介，也不是担保"必须放最前面。定性句是唯一会被记住的句子；如果第一句写"我们会保护你"，后面所有免责都会被大脑跳过。
- **"我们不知道对面是谁"放第一条。** 婚恋类产品的用户默认"平台审过了"，这是最容易被误解的地方，必须先破。
- **不写"提高警惕"。** 无效建议。改为"钱一出现就是诈骗"这种可执行判断。
- **让用户先报警、不是先找平台。** 平台无执法权、无资金追回能力。写"先找我们"是给自己挖坑。
- **末尾留一条不需要隐私成本的退路。** 用户知道"不贴广场也能用"，抵触感会明显下降。

### 2.4 开发实现要点

- 文案以**常量**形式放 `@hongxian/core`，带 `version` 字段；改文案必须升版本号，否则老用户不会再看到。
- 阻塞实现：入口检查 ack，未确认返回结构化 `ACK_REQUIRED` + 全文。
- `ack.json` 只存版本与时间戳，不含任何身份信息。

### 2.5 验收判据（进 TC 用例）

1. 全新环境首次建画像 → 必然出现全文，无法跳过
2. 确认后再次建画像 → 不再出现
3. 文案版本号 +1 → 重新出现
4. `~/.hongxian/ack.json` 存在，且不含任何身份信息
5. **抓包：整个确认动作不产生任何网络请求**

## 3. 防护二 · 举报即断

### 3.1 行为规格（先定行为，再定文案）

举报发生时，服务端必须做三件事：

| # | 动作 | 现状 | 要求 |
|---|---|---|---|
| 1 | **切断该假名 → 举报者的投递通道** | ❌ 只标记 flagged，不阻断 | 服务端拒绝该 `owner_key_id` 对举报者的任何新投递（九类信封全部） |
| 2 | 记录"该假名被举报过" | ✅ 已有（加盐假名 + N=3 → flagged） | 保留 |
| 3 | **不通知被举报者** | ❌ 现在通知本人 | **改为静默** —— 已拍板（§6 决策点 2 取 A） |

**第 1 条的关键设计：阻断必须表现为"投递失败"，与对方静默拒绝不可区分。**

这样同时解决三个问题：
- 举报者不会因为"对方知道我被举报了"遭到报复；
- 被举报者无法通过"是否被拒"反推谁举报了他——因为静默拒绝本来就看不出原因；
- 平台不需要向任何人解释"为什么拒"，因为协议里本来就有拒绝权。

> 这是 D4「静默拒绝」设计的直接复用，不新增协议语义。

**双向闭合**：A 举报 B 后，B 不能投给 A，A 也不再能投给 B。单向阻断会变成"举报后还能继续试探"的漏洞。

### 3.2 文案 A · 给举报者的即时回执

```
已收到，立即生效。

从现在起，他不能再向你投递任何东西——卡片、追问、升级请求，
全部。你们之间这条线已经断了。

接下来会发生什么：
· 这个假名被记了一次举报。这个记录只有他自己能查到，
  不带任何关于你的信息。
· 同一个假名被三个不同的人举报后，进入人工复核。
  在那之前，平台不会自动封禁任何人。宁可慢，也不错杀。
· 如果复核确认他在骗人，会从广场摘掉他的卡，
  并要求他下次发布时重新验证。
  我们不会公开指认任何人——没有这个权力，也不该有。

你现在该做三件事：
· 停止转账。已经转出去的，立刻打 96110 或 110，带着聊天记录和
  转账凭证去报案。我们追不回钱，警察能冻结。
· 保留证据：聊天记录、他的卡片、转账截图。别删。
· 如果他知道你的真实地址或身份，先保证自己安全，再处理别的。

你不用向我们证明什么。举报不需要理由，也不需要证据。
```

### 3.3 文案 B · 给被举报者的通知（**已废弃，仅存证**）

```
有一个假名对你提交了举报。
我们不会告诉你他是谁——不是保护他，是因为我们看不到内容，
本来也不知道你们之间发生了什么。
在复核之前，你的投递功能不受限制。
```

> **决策点 2 已定取 A（静默），此稿不实施，仅留作日后复盘。** 废弃理由见下段。
>
> **注意：这段与 §3.1 第 1 条逻辑上不能共存。** 一旦"举报即断"生效，后半句"投递功能不受限制"就是假的（确实被切断了，只是不知道对谁）。这正是建议改为静默的原因。若保留此稿，必须删掉最后一句，改成"部分投递可能不再送达"——但那等于通知骗子"你被举报了"。

### 3.4 实现要点

- 阻断表：`blocks(reporter_key_id, blocked_key_id, at, reason)`，投递前置检查。
- 阻断**双向**写入（两条记录），查询时任一方向命中即拒。
- 幂等：同一举报者对同一假名重复举报只算一次。
- 举报不消耗"三次未回应"的计数。

### 3.5 验收判据

1. 举报后对方投递 → 响应结构、状态码与"静默拒绝"完全一致（不人为加延时混淆）
2. 重复举报同一人 → N 不重复累加
3. 三个不同举报者 → flagged 生效
4. 被举报者侧收不到任何通知
5. 举报后举报者自己也发不出 → 双向闭合确认

## 4. 防护三 · 贴卡前披露声明

### 4.1 触发与形态

| 项 | 规格 |
|---|---|
| 触发点 | `plaza_publish` 调用时，**在邮箱验证之前** |
| 交互顺序 | 读声明 → 勾选 → 输邮箱 → 收码 → 验证 → 贴卡（一次连续流程） |
| 重复展示 | 首次完整；之后每次一行缩略提示 + 「查看完整说明」 |
| 记录 | 本地 + 服务端都记（`publish_credentials.disclosure_version`）。声明内容对应平台实际行为，必须可追溯 |
| 官网同步 | 全文必须在 `/publish-verify/` 页面可查，**不装工具也能读到** |

### 4.2 文案（建议稿）

```
贴到广场，会多出一条连接。你得先看清楚。

到现在为止，平台只知道"某个公钥做了什么"，不知道这个人是谁。
贴卡这件事，会让你名下的两条记录第一次连起来：

    你的假名公钥  ←→  你的邮箱哈希

也就是说：从这一刻起，平台能确认"这个假名背后的人，有一个能
收到信的邮箱"。四环里，这是唯一一次交叉。

具体存什么：
· 存的是哈希——单向、不可逆，拿到它也算不出邮箱。
· 验证那一瞬间，邮箱明文会在服务器内存里存在几秒，发完信立刻
  丢弃。不写日志，不入库。
· 这个邮箱不能登录、不能找回密码、不会出现在任何卡片里、
  不会展示给任何人、不能用来搜到你。
· 我们不验证你是谁。不知道你的姓名、身份证、住址、工作单位。
  这一层我们做不到——所以不声称做到了。

边界在哪（这段不写，前面的承诺就是假的）：
· 哈希防的是"平台拿着自己的数据库反查邮箱"。它不防"已经知道你
  邮箱的人，拿到数据库后确认你贴过卡"。
· 如果有人同时掌握了你的邮箱和平台的数据，理论上能确认这件事。
  我们不会主动做，但技术上不是"绝对不可能"。
· 所以我们不写"绝对不可关联"。只写我们真做到的部分。

你有两条路：
· 贴广场 —— 需要验证邮箱（就是接下来这一步）
· 只在认识的人之间换卡 —— 全程不需要邮箱，什么都不会多出来

贴出去了，随时可以删。删卡的时候，那条连接一起消失。

[ ] 我明白平台会保存一个与我假名关联的邮箱哈希
```

### 4.3 关键取舍

- **"边界"那一段不能省。** 不写就等于隐含承诺"绝对不可关联"。这句话在出事时会被原文引用为"平台虚假宣传"。写了是诚实，不写是定时炸弹——这是全文最重要的一段。
- **用连接图而不是文字描述。** "两条记录连起来了"一眼能懂，文字描述会被略过。
- **必须给出"不贴广场"这条路。** 给用户一条零隐私成本的替代路径，抵触会明显下降，也更符合"不撮合"的定位。
- **禁用"实名认证""身份验证"。** 一旦出现，等于自己把服务往第 26 条的"信息发布实名"上靠。

### 4.4 实现要点

- `disclosure_version` 入表，改文案不改协议。
- 缩略提示固定一行：`贴广场需要验证邮箱；平台会保存一个与你假名关联的邮箱哈希。查看完整说明 →`
- 声明全文与版本号必须由服务端返回（不从客户端硬编码读），否则改文案要发版。

### 4.5 验收判据

1. 首次贴卡 → 完整声明出现，未勾选不能进入验证
2. 第二次贴卡 → 缩略提示 + 可展开
3. `publish_credentials.disclosure_version` 与当前文案版本一致
4. 官网 `/publish-verify/` 可读到全文（无需安装、无需 JS）

## 5. 禁用词与必用词

| 禁用 | 原因 | 替代 |
|---|---|---|
| 实名认证 / 实名验证 | 我们不是，也不该暗示 | 确认邮箱能收信 |
| 安全 / 保障 / 放心 | 无法兑现 | 写明具体做了什么、没做什么 |
| 绝对 / 百分百 / 永不 | 技术上都做不到 | 写明边界 |
| 审核通过 / 已核验 | 无此流程 | 不出现 |
| 提高警惕 / 保持理性 | 无效建议 | 具体动作（转账就报警） |
| 介绍费 / 谢媒礼 / 礼金 | 涉婚介定性，见定位声明 | 不出现 |

**必用**：具体动词（转账、代付、验证码、恢复短语）、具体号码（110、96110）、具体动作（停止转账、保留截图、离开现场）。

## 8. 协议层增补（举报即断是「零过滤」的唯一例外）

服务端军规是「不审查、不过滤、不评估、不推荐」。举报即断在形式上是对投递的拦截，**必须在协议里写明它是唯一例外**，否则后人会把它当成"过滤功能"的开口，一路加下去，军规就废了。

拟并入协议 v1.4 的条款：

```
§X 投递阻断（delivery block）

平台 MUST NOT 依据内容审查结果阻断任何信封投递。

唯一例外：接收方（reporter）主动提交举报后，平台 MUST 立即阻断该
reporter 与被举报假名之间的双向投递，直至 reporter 撤销。

该阻断的性质是「接收方声明」，不是「平台判断」：
· 平台未读取、未评估任何内容；
· 阻断对双方均不产生可观测差异 —— 被阻断方的投递失败与「静默拒绝」
  在响应结构、状态码、时序上 MUST 完全一致；
· 平台 MUST NOT 通知被阻断方，MUST NOT 告知阻断原因；
· 阻断 MUST 双向生效（A 举报 B 后，A 亦不得再投递给 B）。

阻断不影响身份密钥、不影响信箱读写、不影响与其他假名的投递。
```

**这一条的命门是"接收方声明"而非"平台判断"。** 一旦写成后者，等于平台开始替用户判断内容，四军规当场破掉，且会被当成内容审核的口子。

### 与本文规格的五处差异（都是收紧，不是放松）

1. **`blocks` 存加盐标记而不是 `(reporter, blocked)` 原值。** §7 第 1 步写的是四元组。实现改成 `HMAC(secret, "block|<owner>|<对方>")` 式标记，与举报记录同一手法——否则数据目录里会留下一张「谁断了谁」的明表，拖走即可还原关系图。判"这对断没断"的能力不变。
2. **"与静默拒绝同构"落成"与正常投递逐字段一致"。** 服务端层面并不存在"静默拒绝"这个状态（那是客户端行为）。可观测的等同物只有一种：**发件人看到的就是一次成功投递**，信封沉底不入库。状态码、`id`、`entered_mailbox` 全部一致，且配额照扣（否则"扣不扣次数"就是个探针）。
3. **未提供撤销阻断的接口。** §8 提到「直至 reporter 撤销」，v1 未开这个口子——撤销阻断等于允许"举报后再反悔继续收信"，契约没写清之前不实现。注销时阻断记录一并删除。
4. **防护一的门闩挂在 `interview` 工具上。** 本文写的是 `build_profile`，但当前工具表面没有这个工具名，建画像的唯一入口就是 `interview`，门闩挂在 `interview` 的全部动作上，例外只有 `ack` 与 `unlock`。
5. **披露声明的版本号双向留痕。** 除了本地 `settings.publish_disclosure_version`，还写进 `publish_credentials.disclosure_version`，并由 `GET /v2/publish/credential` 回传（含 `current_disclosure_version` 供比对）——本机记录重装即失，服务端那份才是事后可追溯的凭证。
