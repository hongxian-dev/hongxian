加密一个数据包很简单，难的是**分级授权**。

设想一个场景：你愿意把联系方式给对方，但只想给微信号，不想给手机号。两者在同一个数据包里，如果整个包用一把密钥加密，那你要么全给、要么全不给。这不是产品设计的问题，是加密粒度的物理限制——密钥是解密的单位，密钥给出去，它保护的范围就全开了。

我的项目里这个问题绕不过去，最后做成了"三层信封 + 字段级子密钥"。这篇文章讲这个结构怎么设计，以及几个我踩过的坑。

## 一、先分层：三层，各管一段关系

数据按敏感度分三层，每层一把独立密钥：

| 层 | 内容 | 什么时候能解 |
|---|---|---|
| L1 名片层 | 昵称、年龄段、城市、自我描述 | 交换名片即解锁（互相） |
| L2 深聊层 | 更细的经历、价值观、期望 | 双方同意深聊后（对称互换） |
| L3 见面层 | 联系方式、真实姓名、常去区域 | 双方同意见面后（逐字段授权） |

每层用 AES-256-GCM 独立加密：

```ts
interface CipherBlock {
  nonce: string;  // 12 字节随机 nonce 的 base64；空字符串 = sealed box 模式
  ct: string;     // ciphertext || tag(16B)，整体 base64
}
```

`ct` 里把 16 字节 GCM tag 拼在密文尾部，省一个字段。`nonce` 为空表示用的是 sealed box（临时密钥对协商后一次性加密），定向消息用它，省掉"双方先交换 nonce"这一步。

分层本身不难，难的是 L3。

## 二、L3 的困境：一层密钥管不了逐字段授权

第一版我把 L3 做成一整块密文。问题立刻出现：

- 想给微信号 → 必须把手机号一起给出去
- 想改一个字段 → 整块重新加密，重新授权

这在产品上直接导致一个荒谬的体验：用户为了给一个微信号，被迫交出手机号和真实姓名。大部分人到这一步就退出了。

第二版改成"字段级密钥"：每个字段单独加密。但这带出一个新问题——**密钥从哪来？**

如果每个字段独立随机一把密钥，那密钥数量会爆炸，密钥管理变复杂，且无法从一份备份恢复。正确做法是**从一个主密钥派生**：

```
字段子密钥 = HKDF(L3层主密钥, "l3/<字段名>")
外层密钥   = HKDF(L3层主密钥, "l3/container")
```

这样只需要保管一个 L3 主密钥，字段子密钥随用随派生，不存储。

```ts
// 示意：字段子密钥派生与加解密
function subkey(l3Key: Uint8Array, field: string) {
  return hkdf(l3Key, { info: `l3/${field}`, length: 32, hash: 'SHA-256' });
}

function sealField(l3Key: Uint8Array, field: string, plaintext: string): CipherBlock {
  const key = subkey(l3Key, field);
  const nonce = randomBytes(12);
  const { ct, tag } = aesGcmEncrypt(key, nonce, plaintext);
  return { nonce: b64(nonce), ct: b64(concat(ct, tag)) };
}
```

## 三、为什么 `info` 前缀里的 `l3/` 不能省

HKDF 的 `info` 参数容易被当成装饰，它是**领域分离**（domain separation），作用比看起来大得多。

不加前缀会怎样？所有字段的派生输入退化成"主密钥 + 字段名"。这时如果别处也用同一个主密钥派生别的东西（比如某个协议版本的消息密钥），只要 `info` 撞上，两处就会派生出同一把密钥。这种撞车不会立刻报错，只会让本来隔离的两个用途悄悄共用一把密钥——密码学里最危险的错误就是这种"能跑但已经错了"。

我定的规则是：**任何 HKDF 派生都必须带用途前缀，前缀格式 `<场景>/<细分>`，且全局唯一。** 代码里专门有一个常量文件列全部前缀，加新的必须去那里登记。

`l3/container` 这个前缀是留给外层密钥的——它保护的不是某个字段，而是"这一层整体的结构信息"（字段列表、版本号）。外层和内层分开，是为了让"只解外层不解字段"这种状态存在，检查字段列表而不看内容时用得上。

## 四、字段名要不要加密

这是我纠结最久的一个决定。

如果字段名明文，那么拿到密文的人知道"这个包里有一个 `contact_wechat` 字段"，只是解不开内容。如果字段名也加密，就得解决"怎么知道有哪些字段"——要么全解要么全盲，字段级授权又退回了整层。

我选了**字段名明文**。理由：

1. 字段名是**结构**，不是内容。"对方有微信号这个字段"这件事本身不泄露隐私，因为所有人都有这个字段。
2. 加密字段名会让"选择性授权"无法实现——授权方必须告诉对方"你能解这几个"，那这几个字段名必然暴露。
3. 字段名的取值范围是全站固定的枚举（`contact_wechat` / `contact_phone` / `real_name` / `employer_category` / `hangout_areas` / `photo_refs`），不是自由文本，本身不含个体信息。

这个取舍写进了协议规范，因为它是**明示的安全边界**，不是实现细节。后来的读者需要知道"字段名可见"是设计决定，不是疏忽。

## 五、授权就是给密钥：这件事是不可逆的

字段级子密钥带来的最大问题不是技术，是**语义**。

授权 L3 的语义变成"把某个字段的子密钥交给对方"：

```ts
// grant_l3 信封里带的不是数据，是钥匙
{
  type: 'grant_l3',
  container_key: <l3/container 派生>,
  field_keys: { contact_wechat: <l3/contact_wechat 派生> },
  fields: ['contact_wechat']
}
```

关键点：**钥匙一旦交出去，就收不回来。** 你已经发给对方的密文还在他本地，他随时能用这把钥匙解开。你能做的只有"以后不再给他新数据"，不能"让他忘记已经拿到的"。

这不是实现缺陷，是密码学的固有性质。任何声称能"撤回已授权内容"的方案，要么是假的，要么依赖客户端自觉（不可信），要么需要可信硬件（大部分场景没有）。

我的处理是把这句话明示在授权界面上：

> 你给出去的字段，对方可以永久保存。撤销授权只影响以后，不影响他已经拿到的。

这句话不好听，但它是真的。把它藏起来，用户会在某天发现"我明明撤销了"却不理解为什么对方还知道。

## 六、验签失败必须整包作废，不能降级

信封外层有 Ed25519 签名，覆盖 meta 明文 + 三层密文的哈希。验签失败时怎么处理，是一个容易被"容错思维"带偏的地方。

错误的做法是降级：验签失败就跳过签名、只解能解的层、给个"部分可用"的结果。这个做法的诱惑是"提高可用性"，实际后果是**把签名变成了建议**——攻击者只要破坏签名就能让系统进入无签名路径。

正确做法是整包作废：

```ts
if (!verify(card.meta.sig_public, card.meta, card.hash)) {
  throw new CardRejected('signature_invalid');   // 不降级、不部分解析
}
```

代价是任何一处字节损坏都会让整张卡不可用。接受这个代价的理由：在加密系统里，**"看起来能用但实际不可信"比"明确不可用"危险得多**。用户看到"卡片损坏，请重新获取"会去重取一次；看到一份部分可用的报告，会拿它做决定。

## 七、一个真实的翻车：nonce 复用

写测试时我一度让 `nonce` 从计数器派生，理由是"省随机数调用，还能保证不重复"。跑了 200 多个测试都没问题，直到有一个用例同时加密两个字段。

GCM 的致命要求是**同一密钥下 nonce 绝不重复**。用计数器本身没错，错在计数器的作用域是"整个进程"，而我按字段名重置了它——两个字段用了同一把密钥（如果字段名相同）或同一段 nonce 序列，导致密钥流重叠。GCM 在这种情况下会直接泄露明文异或值，认证也会失效。

修法很简单：每把密钥配一个独立的计数器，或者干脆每个字段都用 `randomBytes(12)`。我选了后者——12 字节随机 nonce 在单密钥加密次数远小于 2^32 时碰撞概率可忽略，而随机比计数器少一个状态要维护。

这件事的教训不是"nonce 要用随机"，而是：**密码学参数的生命周期必须和密钥的生命周期绑定。** 任何"全局的、共享的"状态，在密码学里都值得怀疑。

## 八、这套结构适合什么

| 适合 | 不适合 |
|---|---|
| 分级披露的场景（认识越深看到越多） | 一次全量交换的简单场景 |
| 需要按字段授权的数据包 | 高频大流量（三层加密开销不小） |
| 异步、可离线解密的载体 | 需要频繁更新字段（每次更新要重签） |

第三行是实际使用中的痛点：字段一改，整个包的哈希变了，签名要重做。对名片这种"一次生成、偶尔续期"的载体没问题，对频繁变动的数据就不合适。

## 九、小结

三层信封 + 字段级子密钥，本质是把"授权粒度"从数据包降到字段：

- 分层解决"什么时候能看到什么"
- 字段子密钥解决"能看到哪几个字段"
- 领域分离前缀保证不同用途的密钥不会撞车
- 整包验签失败即作废，不给降级留口子

而它换来的代价是一个必须明说的性质：**授权是发出密钥，发出即不可撤回。**

做这套东西最大的收获不是密码学知识，是学会了区分"技术上能做到"和"语义上成立"。前者靠实现，后者靠诚实。
