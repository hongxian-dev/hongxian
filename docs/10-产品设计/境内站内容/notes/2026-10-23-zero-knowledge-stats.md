做端到端加密的产品，绕不开一个问题：**你自己什么都看不到，怎么知道这东西有没有人在用？**

这个问题很实际。没有数据就没有判断依据——不知道有多少活跃用户、不知道功能有没有人碰、不知道哪天开始下滑了。很多加密产品最后在这里妥协，加了埋点，然后悄悄在隐私政策里写一句"我们可能收集使用数据"。

我的项目选了一条更麻烦的路：把统计拆成三个互不相通的环，每环有不同的信任假设和数据边界。这篇文章讲这个结构，以及它在实现上到底有多简陋。

## 一、先承认矛盾存在

不承认矛盾的方案都是假的。矛盾具体是：

| 想知道 | 需要的信息 | 与零知识的冲突 |
|---|---|---|
| 有多少人用 | 用户数、活跃度 | 冲突小（计数即可） |
| 功能有没有人用 | 行为路径、频次 | 冲突大（要关联到人） |
| 内容是否健康 | 内容本身 | 直接冲突（端到端加密，看不到） |

第三行是绝对的：**端到端加密的产品，在数学上无法做内容审核。** 任何声称"我们既能端到端加密又能审核内容"的说法，要么在某个环节解密了，要么在客户端做了检测（那意味着客户端能看到明文，且要上报结果）。

所以三环制的第一条原则是：**不试图用统计解决内容问题。** 内容问题的解法是举报 + 客户端本地提示 + 明示不审核，不是数据分析。

## 二、三个环，三种信任假设

| 环 | 存什么 | 谁能看 | 保留期 | 隔离方式 |
|---|---|---|---|---|
| **内容环** | 密文信封、加密卡 | 只有收件人（服务端无密钥） | 到期自动删 | 与另两环不同存储目录，代码里不同类型 |
| **聚合环** | 纯计数：用户数、卡数、信封数、被举报数 | 公开（做成透明度页） | 长期 | 只有整数，无任何 ID |
| **行为分析环** | 使用频次、功能路径、设备类型 | 运营方（绑假名，禁关联真实身份） | 短（默认 90 天） | 加盐假名，与内容环不可 join |

关键在于**环与环之间不能 join**。不是"我们承诺不 join"，是数据结构上做不到：内容环的键是 `opaque_id`（公钥指纹），行为环的键是 `HMAC(salt, opaque_id)`，salt 只存在内存且定期轮换——拿着两张表也算不出对应关系。

## 三、聚合环：简陋到只有数文件

这部分我原本以为会很复杂，实际实现只有二十行：

```ts
stats(now = Date.now()): InstanceStats {
  let envelopes = 0;
  for (const box of readdirs('mailboxes')) {
    envelopes += listFiles(`mailboxes/${box}`).length;
  }
  let reported = 0, flagged = 0;
  for (const f of listFiles('reports')) {
    const cur = readJson(`reports/${f}`);
    if (!cur) continue;
    reported += 1;
    if (new Set(cur.reports.map(r => r.reporter_tag)).size >= 3) flagged += 1;
  }
  return {
    identities: listFiles('identities').length,
    cards: listFiles('cards').length,
    envelopes,
    reported_targets: reported,
    flagged_targets: flagged,
    generated_at: new Date(now).toISOString(),
  };
}
```

就这些。数文件个数，返回整数。

这个"简陋"其实是设计结果：因为服务端不存内容，它天然只有"有多少个文件"这种信息。**零知识不是靠加密算法实现的，是靠"根本不存那些字段"实现的。** 表结构里没有的列，泄露不了。

这个端点直接对外公开，做成透明度页。公开的好处是双向的：用户能看到真实数字，我也没法偷偷多收数据——因为公开的口径和代码是一致的。

## 四、加盐假名：为什么不能直接用 ID 去重

举报功能需要"独立举报人数"——同一个人点十次不该算十个人，否则刷举报就能封掉任何人。

最直接的做法是记 `opaque_id` 然后去重。问题是这就在服务端建立了"谁举报了谁"的关系表，一张极敏感的图谱。

改成加盐假名：

```
reporter_tag = HMAC-SHA256(salt, opaque_id)
```

- 同一个人对同一个目标举报多次 → 同一个 tag → 去重生效
- 不同目标之间 → 无法通过 tag 关联（如果每个目标用不同 salt，连"同一个人举报了几个人"都算不出来）
- salt 泄露 → 假名可被还原（这是残余风险，靠 salt 存在内存、定期轮换、不落盘来缓解）

阈值取独立人数 ≥ 3 才标记。取 3 不取 2，是因为两个人可以串通；取 5 又太迟钝，真实受害者的举报会被淹没。这是我拍的，没有严格依据，写在这里免得以后误以为是结论。

**诚实边界**：这个机制防不住"一个人用三对密钥举报三次"。它只防"一个人点三次"。这个限制写在了协议规范里，因为把防护说大了比不说更糟。

## 五、行为分析环：最激进的那一档，和最硬的约束

这一环我没做（代码里没有），只留了设计。原因是它需要先有隐私声明和退出通道，而这两样我还没写。

设计上的约束是四条，缺一条就不能开：

1. **只记频次与路径，不记参数**。记"调用了比对工具"，不记"比对时用了什么条件"——参数里可能含画像内容。
2. **绑假名，禁关联真实身份**。密钥是 `HMAC(salt, opaque_id)`，与服务端身份表用不同 salt。
3. **必须有退出通道**，且退出后立即停止采集，不需要重新注册。
4. **必须有透明页说明**，写清"记什么、不记什么、保留多久"。

这四条里第 3 条最容易做不到——很多产品的"退出分析"实际是"下次启动时生效"，而这段时间的数据已经进库了。要真的做到"退出即停"，采集点必须在写入前检查本地标志，不能靠服务端过滤。

## 六、小样本反推：聚合数据也会泄露

这是我做透明度页时意识到的第二个问题。

如果实例上只有 2 个用户，公开"用户数 = 2"和"信封数 = 7"，再配合公开的时间戳，能推出的东西比想象中多。这类攻击叫小样本反推，在统计披露里是有成熟解法的（差分隐私、最小分组阈值）。

我的处理很土但有效：**透明度页在样本量小于阈值时只显示"数据不足"，不显示具体数字。** 阈值取 100。

这个做法牺牲了"早期也能看到增长"的爽感，换来的是"早期用户不会被公开数据定位"。我认为后者重要得多——冷启动阶段用户最少，恰恰是最需要保护的时候。

差分隐私我没上，因为噪声会让人怀疑数字的真实性，而透明度页的第一要求是可信。这是一个产品判断，技术上有更优解。

## 七、删除：保留期不是"存着但不管"

三个环的保留期不同，删除策略也得分开：

| 环 | 删除方式 | 谁触发 |
|---|---|---|
| 内容环 | 到期清扫 + 用户手动删 + 注销级联删 | 服务端定时任务 / 用户 |
| 聚合环 | 不删（只有整数，无法定位到人） | — |
| 行为环 | 到期滚删（按天分片，整片丢弃） | 服务端定时任务 |

关键点是**内容环的注销必须级联**：删身份记录的同时，删掉这个人投出去的所有信封、贴出的所有卡。如果只删身份，那些密文会变成孤儿——没人能解开，但也没人负责删掉。

我的清扫任务是每小时跑一次，逻辑很简单：遍历，看 `expires_at`，过期的删。简单的好处是能一眼看懂它删了什么，坏处是量大了会慢——到了那个规模再优化，现在不值得。

## 八、这套结构真正解决的是什么

回头看，三环制解决的其实不是"怎么统计"，是**"怎么让自己在诱惑面前没有选择"**。

只要服务端不存内容，就没有"看看用户在聊什么"这个选项；只要行为数据绑的是加盐假名，就没有"这个活跃用户是谁"这个查询；只要聚合数只有整数，就没有"导出用户列表"这个接口。

这些不是靠制度约束、不是靠权限管理、也不是靠"我们承诺",而是**数据从来不存在**。这是我认为唯一可靠的方式——因为制度和权限都会随着人和时间改变，而没存下来的数据永远泄露不了。

代价要说清楚：我看不到内容，就看不到用户在抱怨什么；我不知道谁在活跃，就无法做个性化运营；出了问题只能靠用户主动告诉我。**这是一条明显更难走的路，只有当你确信"不留数据"是产品承诺的一部分时，才值得走。**
