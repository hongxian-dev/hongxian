需求很简单：给网站加一个计数器，只统计"有多少人打开过页面"，不记 IP、不记 UA、不装 Cookie、不引第三方脚本。因为项目承诺不追踪，用 Google Analytics 是说不过去的。

方案也简单：Cloudflare Worker + KV，一个 `/hit` 写、一个 `/stats` 读。我以为半小时能上线。

实际花了一天，三处卡点全都不在业务代码里。写下来，免得下次再踩。

## 一、坑一：上传模块的 Content-Type 决定了它能不能被解析

Worker 的代码是 ES module 形式：

```js
export default {
  async fetch(request, env, ctx) { /* ... */ }
};
```

我用脚本调 Cloudflare 的 API 上传，本地文件明明是对的，接口返回却报：

```
Unexpected token 'export'
```

这个错误的意思很明确：**运行时把这段代码当成了传统 script 解析**，而传统 script 不允许顶层 `export`。

问题不在代码，在 multipart 上传时那个 file part 的 `Content-Type`。我按默认值（`text/plain` 或 `application/octet-stream`）发的，Cloudflare 就按非 module 处理。

正确值：

```
Content-Type: application/javascript+module
```

改完立刻通过。这个坑的特点是错误信息指向代码，但原因在元数据——顺着错误去改代码会一直改不出结果。

排查方法：如果你确定代码本身没语法问题，就去检查上传时每个 part 的 header，别改代码。这条经验在几乎所有"上传脚本"场景都适用。

## 二、坑二：CDN 的安全防护会把自己的客户端拦在门外

计数器上线后，我用浏览器访问没问题。换成 curl 和一段 Python 脚本测试，全部返回：

```
error code: 1010
```

1010 是 Cloudflare 的 Browser Integrity Check 拦截。它检测请求的浏览器特征，不像浏览器的直接拒掉——这是用来挡爬虫和自动化攻击的功能。

问题在于：**我的客户端本来就不是浏览器。** 这个计数器要被一个 Agent 程序调用，它没有 UA、没有 `Accept-Language`、没有正常的 `sec-*` 头。

处理方式是在该域名的安全设置里关掉 Browser Integrity Check：

```
PATCH /zones/{zone_id}/settings/browser_check
{ "value": "off" }
```

关掉之后 curl 正常了。

这里有个判断要说清楚：**关掉 BIC 不等于关掉防护。** 它只是不再按"像不像浏览器"这一条来拒。真正的防刷要靠别的机制（见坑三）。如果你在做一个面向浏览器的站点，不该关它；如果端点本来就是给程序调的，它只会误伤。

另一个细节：关掉 BIC 后我把 `User-Agent` 要求也去掉了——因为要求 UA 等于要求客户端伪装，与"不追踪"的立场自相矛盾。

## 三、坑三：KV 是最终一致的，计数会"倒退"

KV 的读在边缘节点缓存。写入后立刻在另一个节点读，可能读到旧值。

这对计数器的影响是可见的：用户刷新页面，看到的数字可能变小。

我一开始想用"每次读都回源"来绕过，但 KV 没有强制回源的开关（有 `cacheTtl` 参数可以设成 0，仍不保证强一致）。

真正的解法是**改变对数字的承诺**：

1. **不做实时显示**。`/stats` 返回的数字标 5 分钟缓存（`Cache-Control: max-age=300`），并接受它是个近似值。
2. **写入用"增量"而不是"读改写"**。KV 没有原子自增，读改写会丢更新。我的做法是**不存总数，存按天分片的键**（`hits:2026-10-24`），读的时候把最近 N 天加起来。写入只做"读-加-写"在单片上，冲突窗口小到可以忽略，且丢一次更新只影响一天的一个数字，不影响总量口径。
3. **口径写清**。透明度页写明"数字为近似值，5 分钟更新，不含去重"。

第 2 点是关键：**在没有原子操作的存储上，不要做"精确计数"，做"可容忍误差的计数"。** 想要精确，就该换 Durable Objects 或者干脆上数据库——但那也意味着更重的运维，对一个计数器不值得。

## 四、顺手做的两件事

### 4.1 防刷：工作量证明

完全开放的计数器可以被脚本刷到很高，数字就失去意义。加验证码太重（还要引第三方），我用了一个很土的办法：**工作量证明**。

客户端请求 `/challenge` 拿到一个随机串，然后找一个 nonce 使得 `SHA-256(challenge + nonce)` 的前 4 个字节为 0（难度 4，约 2^32 次哈希）。把结果提交给 `/hit`，服务端验一次哈希就放行。

```js
// 客户端：找 nonce（示意）
let nonce = 0;
while (true) {
  const h = await sha256(challenge + nonce);
  if (h[0] === 0 && h[1] === 0 && h[2] === 0 && h[3] === 0) break;
  nonce++;
}
```

难度 4 让浏览器多跑几百毫秒到几秒，脚本刷量的成本相应上升。它挡不住有决心的人，但筛掉了随手刷的。

**这个方案的最大好处是零依赖**：不需要验证码服务、不需要用户交互、不需要存会话。

### 4.2 不记 IP

计数器最容易被忽略的泄露点是日志。默认情况下 Cloudflare 会记录请求信息，worker 里如果顺手 `console.log(request.headers.get('cf-connecting-ip'))`，那"匿名计数"就成了笑话。

我的做法是代码里**根本不读 IP 相关的头**，也不 log 任何请求头。只有 `env.HITS.put()` 和 `env.HITS.get()`。

这算是一种"用代码结构保证承诺"：不是承诺不记，是没有那条代码路径。

## 五、自定义域与证书

Worker 默认给你一个 `xxx.workers.dev` 域名。这个域名在国内的可达性很不稳定，实测经常连不上——如果你的用户在国内，**必须绑自定义域**。

绑定的步骤是 DNS 加一条记录指向 Worker，Cloudflare 自动签发证书。注意这里必须用**橙云代理**（这是 Worker 路由的必要条件），与"服务器直连要用灰云"的规则相反。这点容易搞混：

| 场景 | 云朵状态 | 原因 |
|---|---|---|
| 指向源站服务器（如香港 VPS） | 灰云（DNS only） | 橙云会绕行境外节点，国内延迟变高 |
| 指向 Worker | 橙云（Proxied） | Worker 只能在 Cloudflare 边缘执行 |

## 六、结果

最终形态：一个 80 行的 Worker，两个端点，KV 按天分片，PoW 难度 4，5 分钟缓存，不记 IP 不记 UA。成本在免费额度内。

它做得不好的地方也很清楚：

- 数字是近似的，会滞后
- PoW 让首次加载多了几百毫秒
- 挡不住有決心的刷量（只能事后看趋势异常）
- KV 的日分片方案读取时要遍历多天，天数多了会变慢（我的处理是只保留最近 90 天）

但这些缺点都是**已知的、写在文档里的**，而不是"发现时才知道"。我认为这比"功能更强但边界不清"要好。

## 七、三条能带走的经验

1. **报错信息指向的地方不一定是错的地方。** `Unexpected token 'export'` 让我去改代码，实际要改的是上传时的 Content-Type。
2. **CDN 的安全功能默认是按"人类浏览器"假设设计的。** 给程序用的端点，第一件事是确认这些假设会不会误伤自己。
3. **在没有原子操作的存储上，别承诺精确。** 改承诺比改架构便宜，且更诚实。

第 3 条是这次最大的收获。它不限于 KV——任何"最终一致"的系统（缓存、搜索索引、消息队列）都在逼你做同一个决定：要么改架构，要么改对用户的承诺。
