MCP Server 的第一版我写了 400 行，21 个工具全在一个文件里，每个 handler 里做参数解析、业务判断、文件读写、拼返回文案。能跑，测试也过了。

三个月后我想改一个匹配规则，发现要动七个 handler，而其中四个的改动方式还不一样——因为它们在复制粘贴时被我"顺手优化"过。

这篇文章讲我怎么把它拆开，以及拆的过程中总结出的几条规则。不是 MCP 的入门（那个看官方文档就行），是**结构上的取舍**。

## 一、先分清三种代码

MCP Server 里的代码其实只有三种，混在一起才出问题：

| 类型 | 职责 | 变化频率 | 该住在哪 |
|---|---|---|---|
| 协议适配 | 参数解析、结果序列化、错误格式 | 随 MCP 规范变 | MCP 层 |
| 领域逻辑 | 真正的业务规则（怎么算、怎么判、怎么排） | 随产品变 | 独立的纯函数包 |
| 状态与 IO | 文件读写、网络请求、时间戳 | 随环境变 | 注入进来的接口 |

多数 MCP Server 的长相是：这三层被写进了同一个 `async (args) => {}`。

薄壳的意思不是"代码少"，是**适配层不拥有任何判断**。一个合格的 handler 读起来应该像这样：

```ts
// MCP 层：只做三件事——解参数、调 core、包结果
handler: async (args) => {
  const input = CardInput.parse(args);          // 1. 解参数（schema 校验）
  const result = computeMatchReport(input);      // 2. 调纯函数
  return text(result.summary);                   // 3. 序列化
}
```

`computeMatchReport` 里没有 `fs`、没有 `fetch`、没有 `Date.now()`。它是 `(input) => output` 的纯函数，可以在单测里跑一万次不产生副作用。

## 二、四层怎么切

我的项目最后切成四个包：

```
packages/
├── schema/   # 数据结构与校验（零依赖，只有 zod）
├── core/     # 领域逻辑（纯函数，不碰 IO）
├── mcp/      # MCP Server：工具表面 + 适配（依赖 core + schema）
└── server/   # HTTP 服务端（独立部署，不依赖 mcp）
```

这四层的依赖方向是单向的：`mcp → core → schema`，`server → schema`（不依赖 core）。

**关键设计**：`server` 不依赖 `core`。服务端只是一个加密信箱，它不需要知道"怎么算匹配"。如果服务端依赖了 core，就会出现"客户端逻辑改一行，服务端要重新部署"——而这两个东西的发布节奏完全不同。

依赖方向错了，比分层错了更难发现。因为编译能过、测试能过，问题只在运维时刻暴露：想单独升级客户端，发现服务端也得跟着发。

## 三、工具表面怎么分组

21 个工具如果平铺，用户（或者说用户的 AI）根本不知道什么时候该用哪个。分组的依据不是技术相似性，是**用户此刻在做什么**：

| 组 | 数量 | 场景 |
|---|---|---|
| 基础 | 12 | 建画像、签发/导出/导入卡片、比对、投递与接收、账本、教练、备份恢复擦除 |
| 轮次与见面 | 4 | 推进一轮对话、见面锦囊、见面复盘、查看已解锁的见面层 |
| 平台 | 5 | 广场浏览/发布、经平台投递、拉信箱、举报 |

分组的判断标准是：**同一个用户意图下的工具，命名要能让人猜出来。** `sign_card` / `export_card` / `import_card` 三个词用同一套动词范式；而 `round` 这种短词要配一段足够长 description，否则 AI 会误判为"轮询"。

除了工具，还有 8 个 prompts。这点常被忽略——**prompt 也是工具表面的一部分**，因为它决定了 AI 在什么时机做什么。把"安全与反诈终检"做成 prompt 而不是硬编码进工具返回，好处是它可以被宿主界面直接触发，也能被用户主动调取。

## 四、无状态工具，状态放文件

MCP Server 跑在宿主的进程里，生命周期不由你控制：宿主重启、会话切换、用户点了个"新对话"——内存里的东西就没了。

所以我的工具全部是无状态的，状态落在本地文件：

```
~/.hongxian/
├── identity.json      # 密钥对（权限 600）
├── profile/           # 画像（版本化，每次重签留旧版）
├── cards/             # 已签发与已导入的卡
├── ledger/            # 姻缘线账本
└── cache/             # 广场拉取的存证
```

这么做的代价是每次工具调用都要读文件。对低频操作（建画像、出卡、比对）完全无所谓；如果你在做高频调用的工具，这条路不合适。

好处比代价大得多：

1. **崩溃不丢状态**。进程被杀，数据还在。
2. **用户能看见**。用户可以直接打开文件夹，看到自己有什么数据——这是零知识承诺的一部分，不是"额外的透明度功能"。
3. **删除是真的删除**。擦除工具就是删目录，不需要跟任何服务端协调。
4. **测试好写**。把 `HOME` 指到临时目录，就能跑完整的 E2E。

第 2 点值得强调：**如果宣称不收集用户数据，那么"用户能看到自己的全部数据在哪"就是承诺的一部分，不是加分项。**

## 五、返回值：写给谁看

MCP 工具的返回值最终会被 AI 读，然后由 AI 转述给人。这个链条决定了返回文本的写法：

| 错误类型 | 写什么 | 为什么 |
|---|---|---|
| 参数错了 | 哪个字段、期望什么、实际是什么 | AI 需要自己纠正并重试 |
| 前置条件不满足 | 缺什么、怎么补（下一步动作） | AI 需要引导用户 |
| 环境错误 | 原始错误 + 可能原因 | 人要能据此排查 |

反例是我最早写的那种：

```ts
return text('操作失败');
```

这句话对 AI 是死路——它不知道该重试、该改参数、还是该告诉用户放弃。改成：

```ts
return text('无法签发卡片：画像尚未完成第三轮访谈（当前 2/3 轮）。请先完成剩下的一轮。');
```

差别不在信息量，在**可操作性**。工具返回是给一个"会自己想办法的调用方"看的，不是给人看的日志。

## 六、不要在文档里写死数量

这是一个小坑但值得单独说。我早期在 README 里写"提供 20 个工具"，加了第 21 个之后忘了改，读者以为文档过期，实际是文档错了。

改成从代码派生：

```ts
export const TOOL_COUNT = TOOLS.length;
export const PROMPT_COUNT = Object.keys(ALL_PROMPTS).length;
```

日志、文档、健康检查都读这两个值。原则很简单：**凡是能被计算出来的数字，不要手写。** 手写的数字会在第一次改动时变成谎言，而没人会记得回来改。

## 七、测试怎么分工

分层之后，测试也跟着分层，各管一段：

| 层 | 数量级 | 测什么 | 为什么放这层 |
|---|---|---|---|
| 单测（core） | 283 | 规则是否正确：加解密、签名、档位判定、预算累计 | 纯函数，快、可穷举边界 |
| E2E（mcp） | 123 | 工具之间能否串起来：建画像 → 出卡 → 导入 → 比对 | 真实调用路径，能抓出参数契约不一致 |
| 服务端 E2E | 21 | 端点语义与安全不变量：冒用 ID、重复投递、过期拒收 | 需要真实 HTTP |
| 宿主冒烟 | 20 | 真子进程、真 STDIO，宿主能不能启动它 | 只有真的起进程才能发现 |

最后一行是我最晚补的，也是最值的：前面所有测试都在同进程里跑，宿主实际是通过 STDIO 子进程通信的。协议对不对、启动参数对不对、stderr 会不会污染输出——这些问题只有真起一个进程才暴露。

冒烟测试的写法很土：`spawn` 一个 node 进程，喂一行 JSON-RPC 进去，读一行出来，断言。但它抓到过两个真实问题：启动时打印的一行日志污染了 stdout，以及一个工具的 schema 在序列化时丢了必填标记。

## 八、几条能直接用的规则

如果只记四条：

1. **适配层不写 `if` 判断业务**。看到 handler 里有业务分支，就是该下沉的信号。
2. **IO 从注入来**。`Date.now()`、`fs`、`fetch` 直接调用会让纯函数变成不可测函数。
3. **返回文本要能被下一代 AI 用来决定下一步**，不要写给日志看。
4. **依赖方向单向且清晰**。客户端与服务端不该共享领域逻辑，只共享数据结构。

第 4 条最难坚持，因为共享代码一时爽。但它决定了两边能不能独立发布——而独立发布是这类项目长期活下去的前提。

## 九、小结

薄壳不是架构洁癖，它解决的是两个具体问题：改一处不动七处，以及测逻辑不用起服务。

而这两件事的价值，只有在项目活过三个月之后才显现——所以它总被排在"先跑起来"之后。我的建议是反过来：**第一次写 handler 的时候就分三行**（解参数、调 core、包结果），成本是零，收益在三个月后。
