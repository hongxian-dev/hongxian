我在做一个端到端加密的开源项目，做到注册这一步卡了三天。卡的不是技术，是觉得整件事别扭：一个宣称"看不到你内容"的服务，注册时第一件事是让你交出邮箱和密码。

这两件事并不矛盾——加密的是内容，注册是账号体系。但工程上它带来一个持续的消耗：只要系统里有邮箱，就有找回密码、改密码、异地登录提醒、邮箱被撞库后的一串麻烦，而这些东西对"只做加密转发"的服务来说全是纯负担。

后来我把注册整个删掉了，换成一对密钥。这篇文章讲这个做法省掉了什么、欠下了什么，以及几个容易做错的地方。

## 一、先把"身份"和"加密"拆成两把钥匙

最常见的错误是用同一对密钥既签名又加密。RSA 时代这么干勉强能跑，到椭圆曲线这里就出问题了：Ed25519 是签名算法，X25519 是密钥协商算法，它们的数学结构和用途都不同，混用会引入跨协议攻击面。

所以第一件事是把两把钥匙分开：

| 密钥 | 算法 | 用途 | 是否公开 |
|---|---|---|---|
| 身份密钥 | Ed25519 | 签名：证明"这条消息是我发的" | 公钥公开，私钥永不离开设备 |
| 协商密钥 | X25519 | 加密：让对方能安全地把会话密钥送给我 | 公钥公开，私钥永不离开设备 |

各 32 字节私钥、32 字节公钥。两把私钥一起存在本地，从不外传。

这个拆分有一个直接的好处：**签名公钥可以独立地充当身份标识**，因为它只用于验签，泄露了也不影响机密性。而协商公钥换了不影响"我是谁"——设备迁移时换一把协商密钥，身份不变。

```ts
// 示意：两把密钥的生成与派生
const sig = ed25519.generateKeyPair();   // 签名用
const kx  = x25519.generateKeyPair();    // 协商用

// 账号 ID 不是随机分配的，而是签名公钥的指纹
const opaqueId = base64(sha256(sig.publicKey));  // 32 字节
```

## 二、公钥即账号：服务端只存指纹

传统账号体系里，服务端知道"这个邮箱对应这个人"。改成密钥后，服务端看到的是：

```
opaque_id = SHA-256(签名公钥)     // 32 字节，base64
+ 签名公钥                        // 用于验签
+ 协商公钥                        // 用于投递加密信封
```

没有邮箱、没有手机号、没有密码哈希。注册接口的输入就是这三个值，服务端做一次形状校验（是否恰好 32 字节的 base64）就存下。

这里有一个必须做对的检查，我一开始漏了：

> **`opaque_id` 必须由服务端重新计算并校验等于 `SHA-256(公钥)`，不能信任客户端提交的值。**

漏掉的后果很直接：任何人都可以拿着自己的密钥，用别人的 `opaque_id` 去注册，把对方在服务端的记录顶掉或消耗掉对方的配额。这是一个纯粹的身份冒用漏洞，而且因为服务端"什么都没存"，它不会有任何日志能事后发现。

修法只有一行，但性质完全不同：

```ts
// 服务端：拒绝 id 与公钥不匹配的注册
if (body.opaque_id !== base64(sha256(fromBase64(body.sig_public)))) {
  return c.json({ error: 'opaque_id_mismatch' }, 400);
}
```

这条不变量后来被我当成整个服务端的安全底线——**凡是客户端提供 ID 的地方，都要能用公钥重算一遍**。

## 三、恢复短语：24 个词的取舍

密钥即身份最尖锐的问题是：私钥丢了，身份就没了。没有"忘记密码"，也没有任何人工途径能帮你找回。

唯一的补法是恢复短语。用 BIP39 的 24 个英文单词编码 256 位熵，抄在纸上：

```
witch collapse practice feed shame open despair creek road again ice least
...（共 24 词）
```

为什么是 24 词而不是 12 词？12 词是 128 位熵，够用；24 词是 256 位，与私钥长度对齐。多出来的冗余在这个场景里不是必需，但我选了 24 词，理由很实际：**用户对这个东西的信任度，和对"看起来够长"的直觉成正比**。这不算严谨论证，是一个产品判断，我把它写在这里以免自己以后误以为是技术结论。

工程上要注意三件事：

1. **恢复短语只能用于重建身份密钥**，不要用它派生加密密钥。一旦同一个种子派生出多种用途的密钥，某一处泄露就会牵连其他。
2. **校验和必须用**。BIP39 自带 8 位校验和，抄错一个词有 255/256 的概率被检出。不做校验的话，用户会在几个月后发现恢复失败，而那时已经无法补救。
3. **不要提供"把短语存在云端"的选项**。这看起来是体贴，实际是把唯一的离线备份变成在线资产，同时把零知识的承诺打了个折。

## 四、代价：几个没法绕过去的问题

诚实地列一下这套设计的欠账，因为网上讲"无密码登录"的文章大多只讲好处。

### 4.1 多设备是硬骨头

一台设备一把密钥时，"在手机上也能用"就变成了一个协议问题。可选的路只有三条：

| 方案 | 做法 | 代价 |
|---|---|---|
| 短语重建 | 新设备输 24 词，生成新的密钥对 | 身份 ID 变了，或者说需要"同一身份、新公钥"的映射 |
| 设备间迁移 | 旧设备把私钥加密后传给新设备 | 需要一条可信的近场通道（二维码、局域网） |
| 多设备多密钥 | 一个身份下挂多把公钥 | 服务端要支持一对多，签名验证变复杂 |

我选了第一种加第二种的组合：短语重建保证"永远能回来"，设备迁移保证"日常不折腾"。这意味着服务端必须允许**同一身份的签名公钥变更**，而这又引出下一个问题——公钥变更时，怎么证明是本人？

答案是：用旧密钥签一条变更声明。如果旧密钥已经丢了（只能靠短语重建），就用短语派生的根密钥签。这就是为什么根密钥和身份密钥要分层：根密钥不动，身份密钥可轮换。

### 4.2 密钥丢失等于身份丢失，这句话必须写在明面上

产品文档里我写了一句话，写在恢复短语生成的那一屏：

> 这 24 个词是唯一能恢复你身份的东西。丢了它，这个身份就永久消失了，我们没有任何办法帮你找回来——因为我们在设计上就不知道你是谁。

这句话不好听，但它是这套设计的真实成本。把它藏起来可以让注册转化率好看一点，代价是用户在真的丢失时觉得被骗。

### 4.3 无法主动封禁"人"

因为没有身份信息，运营方封禁的只能是"这个公钥"，而对方换一对密钥就能回来。对有实名要求的场景，这套设计根本不能用——这是它最硬的适用边界，不是能靠工程弥补的缺陷。

我在项目里对这件事的处理是：不假装能解决，而是把封禁做成"限速 + 举报标记"，并在协议里写明它防不住换号。

## 五、服务端视角：注册到底变成了什么

换个角度看，注册从"创建一个用户"变成了"登记一个公钥"：

```
POST /identity/register
{ opaque_id, sig_public, kx_public }

→ 201 { instance, registered_at }
```

没有会话，没有 token，没有 cookie。每次请求用签名认证：

```
签名内容 = 方法 + 路径 + 时间戳 + 请求体哈希
请求头   = X-Opaque-Id, X-Timestamp, X-Signature
```

服务端验签通过即认为是本人。时间戳用于挡重放（窗口 5 分钟）。

这套东西的好处是服务端**完全无状态**——不需要 session 存储，重启不丢登录态，横向扩展不用考虑粘性会话。副作用是每个请求都要做一次验签，CPU 开销比查 session 高，但对一个低频的加密转发服务来说完全不是问题。

注销也很干脆：删掉这个 `opaque_id` 下的全部密文和公钥记录。因为没有关联的身份信息，删完就是真的没有了——这反而让"一键注销"变得可信，不需要向用户解释"我们保留了哪些数据"。

## 六、什么时候不该这么做

我不想把这套做法说成普适方案。它适合的场景很窄：

| 适合 | 不适合 |
|---|---|
| 端到端加密、内容对服务端不可见 | 需要实名、需要内容审核 |
| 用户是开发者或技术型用户 | 面向大众消费者、要求"扫码即用" |
| 低频、异步的交互 | 强实时、要求多端同时在线的 IM |
| 能接受"丢失即失去" | 有资产、有交易、有法定留存义务 |

最后一条尤其重要：任何涉及钱或法定责任的东西，都不该只靠一把本地密钥。

## 七、小结

这套设计的核心其实只有一句话：

> **把身份从"服务端记住的一个账号"变成"你自己持有的一对密钥"。**

省掉的是密码、邮箱、找回流程、会话存储和一整类撞库风险；欠下的是密钥管理、多设备协议、以及"丢了就没了"的冷酷。

这笔交易值不值，取决于你的产品能不能接受后者。我的项目能，所以我做了这个选择；但如果你在做的是一个要让父母那辈人用的东西，答案很可能是不能。
