## 4. 广场卡的 key_l1 问题与解法（V6 详述）

**问题**：v1 的匹配卡信封 = meta + 三层密文 + `key_l1`（明文随卡，导入方持卡即解 L1——文件直交模式成立）。广场卡经服务端存储转发，若 `key_l1` 随 blob 上传，**服务端持有即可解密 L1**，直接违反宪法 §4 零知识（"平台能接触到的最多只是用户公钥 + 加密 blob，无法解密内容"）与 v2 初稿 §3（服务端只见密文）。

**已评估的替代方案**：

| 方案 | 结论 |
|---|---|
| key_l1 用公开常量派生（HKDF(plaza-salt)） | ✗ 恶意运营者可推导——政策级零知识，非密码学级；宪法明确"零知识架构是堵信任缺口唯一硬手段" |
| L1 明文随卡（放弃加密） | ✗ 更差，同等泄露还丢了 at-rest 加密 |
| 广场卡不展示 L1，浏览只见 declared_filters 粗字段 | △ 宪法顺带解决（§3 分拣极限），但产品丰富度大降 |
| **剥离 key_l1 + grant_l1 密封交付** | ✓ 采用 |

**解法（v2.0）**：

1. 月老上传广场卡时生成 `plaza_card` 变体 = 卡信封去掉 `key_l1` 字段（签名对象随之调整，签名仍覆盖 meta+三密文）；
2. 广场浏览态（任何人拉取）：只见 meta（opaque ID、sig_public、kx_public、TTL、类型）+ 三密文。客户端本地能做的唯一事：验签、看 TTL、存证。**没有任何可展示内容**——发现机制降级为"只能看到有人在，看不到他是谁"；
3. 兴趣触发：请求方月老发 `upgrade_request` 信封（定向，含请求方 kx_public）；
4. 卡主月拉拉取信箱看到请求 → 主人决定是否应答 → 应答 = `grant_l1` 信封（L1 密文 + key_l1，sealed box 至请求方 kx_public）；
5. 请求方解密即得 L1 全文明文——**"解锁一阶"从 v1 的"文件易手即解锁"变为显式授权动作**，与三阶信息阶梯（L1→L2→L3 逐阶 opt-in）语义完全对齐。

**产品代价（诚实记录）**：陌生人发现从"翻名片"变成"看见轮廓→敲门→等主人开门"。慢，但每一步都是授权。卡主侧新增"应答请求"手势（月老提示，不自动）。此决策改变 v1 README 中"对方将看到什么"的广场版表述，需同步修订网站文案——**待孙超 ratification 后执行**。

## 6. 服务端 API v1（终稿，军规逐条过）

```
POST /v2/identity/register     自声明 opaque ID（服务端不验证、不存任何身份秘密）
GET  /v2/identity/:opaque_id   存在性查询（返回 200/404，无其他信息）
POST /v2/cards                 贴广场卡（plaza_card 变体，密文 + meta + TTL；重签覆盖）
GET  /v2/cards?cursor=...      增量拉取广场卡池（cursor 分页；哑管道——零过滤零排序）
DELETE /v2/cards/:fingerprint  撤卡（签名持有者）
POST /v2/mailbox/:address      投递信封（定向；限速 20/日；返回"已入信箱"）
GET  /v2/mailbox?cursor=...    拉取自己的信件（cursor 分页）
DELETE /v2/mailbox/:id         删除单封信（收件方）
DELETE /v2/identity            注销（密文全删；无实名记录可删——v2.0 无实名层）
```

军条对照：无 `/match`、无 `/recommend`、无 `/search`、无排序参数；投递只接受点对点地址；无在线状态端点；无已读回执字段。**哑管道**：`GET /v2/cards` 返回全量池（cursor 顺序 = 上传时间序，仅分页不筛选），过滤 100% 在客户端。

## 9. 月老 Skill 接入接口（M1.3 定稿，2026-10-19）

### 9.1 工具面（mcp 包 12 → 16 工具）

| 工具 | 入参 | 行为 | 军规落点 |
|---|---|---|---|
| `plaza_browse` | `server?`、`cursor?` | 拉全量池 → 本地验签/过滤（去自/去黑/去重/TTL）→ **存证落盘**（`cards/plaza/<hex>/<card_id>.json`）→ 返回轮廓 JSON | 哑管道：零过滤零排序在服务端，分拣 100% 本地；只见"有人在" |
| `plaza_publish` | `action=publish\|withdraw\|status`、`server?`、`my_card_id?`、`fingerprint?` | 匹配卡 → `plaza_card` 变体（**自动剥离 key_l1**、换 card_id、重签、三层密文原样保留）→ POST /v2/cards；撤卡按指纹；状态查注册+已贴卡 | §10.5 本地闸门（贴前再验无 key_l1）；一人一卡重签覆盖 |
| `send_via_server` | `msg_type`、`target_card_id` 或 `target_address`、`body`、`server?` | 信封构造（补全+校验+签名）→ POST /v2/mailbox/:address → 返回**仅"已入信箱"** | V9：无回执无 presence；投递只接受点对点地址 |
| `mailbox_pull` | `server?`、`keep_on_server?` | 循环分页取尽 → 逐封验签 → 路由（与 receive_envelope 同一实现）→ **POP3 式拉取即删**（本地处理成功后才删服务端） | 拉取无推送；服务端少一分持有少一分责任 |

**共享实现**（tools-exchange 抽出，文件流/广场流一个实现）：
- `completeMessageBody(msgType, body, session, store)`——`upgrade_request` 缺省补 `requester_kx_public`（本方协商公钥，v0.4 必填）；`grant_l1` 由 `card_fingerprint + requester_kx_public` **派生** `sealed_key_l1`（本方 L1 层密钥密封——密文构造是工具职责，LLM 不碰密钥）；
- `buildSignedEnvelope(...)`——meta + sealed 消息体 + Ed25519 整体签名；
- `routeEnvelope(env, session)`——拉黑检查 → 建线 → 解封 → 按 msg_type 分流。**广场/文件双流判别**：`target_card_id` 命中本方已贴广场卡且一阶未解锁 → 敲门流（指引 grant_l1）；否则 L2 深聊流。`grant_l2` 层密钥改为合并写（不清掉已解锁的 key_l1——V6 与 D5 叠加的场景）。

### 9.2 客户端侧机制（server-client.ts，协议 §7 独立实现）

- **认证头**：`X-Hongxian-Auth: <opaque_id>:<ts>:<sig_b64>`，签名对象 `canonical({opaque_id, ts, action})`，action = `"METHOD /路径"`（**未编码地址**；URL 路径中的地址 `encodeURIComponent`——base64 含 + /，两端口径以 E2E 锁定）；
- **注册**：lazy 幂等（409 = 已注册即对齐本地记录）；`opaque_id = SHA-256(sig_public)` 指纹注册绑定；状态落 `server/registration.json`；
- **实例地址**：`settings.plaza_instance` 持久化——任意广场工具显式传 `server` 即记住；未配置时返回自托管引导（docker compose up 后传地址）；
- **本地历史**：`server/plaza-seen.json`（已浏览卡，500 条环形）、`server/pulled.json`（已拉取信封 id，幂重）；
- **backup/restore 扩展**：档案纳入 `cards/plaza-mine`、`cards/plaza` 缓存、`server/*` 状态——换设备不掉广场状态；
- **wipe 级联**：锁定前尽力 `DELETE /v2/identity`（需持钥签名）；失败不阻塞本地删除，提示 TTL 自动清扫兜底。

### 9.3 验证证据（M1.3 验收）

- 单测 **206/206**（18 文件；新增 core plaza 16 + mcp 21：认证头真验签/实例解析/注册历史/消息体补全派生/双流判别/拉黑/层密钥合并）；

## 10. Schema v0.5 · declared_filters（D8 圈层落地，2026-10-22）

**问题**：V6 剥离 `key_l1` 后，广场浏览方在 `grant_l1` 之前解不开 L1，`CardMeta` 又没有任何可过滤明文字段——D8 的"声明式圈层"在 v2.0 只剩一句口号：用户只能看到"有人在"，无法按同城/年龄/方向筛选。

**V10 决策（新增）**：把**主人自己声明要公开**的五个粗字段放进 meta 明文（不是画像内容），服务端仍是哑管道，过滤 100% 在客户端。

| 字段 | 约束 | 说明 |
|---|---|---|
| `gender` / `seeking` | `female`/`male` | 方向性**双向**校验：我要的性别 = 对方性别，且对方要的性别 = 我 —— 单向窥探不可表达 |
| `city` | 6 位 GB/T 2260 | 到市为止，不收区县与地址 |
| `age_band` | 与 L1 同词表 | — |
| `visible_to` | `all` / `same_city` / `same_age_band` | 可见性声明圈 B；无法确认即不展示 |

铁律：
1. 声明在 `meta` 内 → **被签名覆盖**，服务端与第三方改不了；
2. `match_card` 携带 `declared_filters` = 非法信封（私交名片没有圈层消费者）；
3. 空对象非法（"我声明了"却什么都没声明会误导对方）；
4. 过滤在客户端（`core.filterPlazaPool`），服务端 `GET /v2/cards` 仍返回全量池；
5. **诚实边界**：`visible_to` 靠客户端受信执行，改造过的客户端可以无视——但它依然读不到一个字节的名片（没有 `grant_l1` 就没有 `key_l1`）。

**默认策略（产品纠偏）**：浏览**不**从画像自动派生圈层。月老不能替主人决定"只看同城"——那会让两个没声明的人互相看不见，是最坏的产品事故。只有主人显式传 `my_filters` 才生效，并记住（`settings.plaza_circle`）。

## 11. 举报机制（v2 初稿 §6 落地，2026-10-22）

零知识的代价必须诚实设计：**服务端读不到信件，就没法审核证据**。因此举报只能是行为信号。

```
POST /v2/reports      { target_opaque_id, reason_code }   ← 举报人持钥签名
GET  /v2/reports/:id  → { reports, distinct, flagged }     ← 只有被举报者本人可查
```

| 规则 | 值 | 理由 |
|---|---|---|
| `reason_code` | 受控枚举 5 项 | 一旦允许自由文本，举报就变成了内容审查通道 |
| 举报人 | 加盐假名 `SHA-256(secret \| opaque_id)` | 可去重，但数据目录被拖走也反查不出"谁举报了谁" |
| 计数 | 按**独立举报人**；N=3 → `flagged` | 一个人刷不出效果 |
| 谁能看汇总 | 只有被举报者本人 | 公开举报数会变成羞辱工具 |
| `flagged` 的效果 | "值得运营者看一眼" | 协议不做裁决；不服就换实例，身份不变 |

## 12. 实例匿名聚合（M4 的一部分，2026-10-22）

```
GET /v2/stats → { identities, cards, envelopes, reported_targets, flagged_targets, generated_at, instance }
```

只有总和：无 opaque ID、无个体活跃度、无内容、无排序。与 v1 计数器页同一条纪律。
