## 1. 记录形态：3 条，不是 5 条（2026-10-24 实测修正）

> ⚠️ **本节曾在 v1.0 写错。** 当时依据搜索引擎里的旧资料，写成「AWS SES 形态：1 MX + 1 TXT SPF + 3 条 DKIM CNAME」。实际打开 Resend 控制台后发现，Resend 已迁到自有基础设施 `forge.rmta.net`，形态完全不同。**以下为 2026-10-24 从 Resend 后台 Records 页逐条核对后的正确形态。**

Resend 对一个域名只要求 **3 条记录**，**没有 MX**：

| # | 类型 | Cloudflare 的 Name 填 | Content（从 Resend 复制） | 代理状态 |
|---|---|---|---|---|
| 1 | TXT | `resend._domainkey.mail` | `p=MIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQ...IDAQAB`（约 218 字符） | 不适用 |
| 2 | CNAME | `rsend.mail` | `rsend-apne1.forge.rmta.net` | **DNS only（灰云）** |
| 3 | CNAME | `send.mail` | `send.forge.rmta.net` | **DNS only（灰云）** |
| 4 | TXT | `_dmarc`（根域，**不带 mail**） | `v=DMARC1; p=none; rua=mailto:<你的真实邮箱>; pct=100` | 不适用 |

前 3 条是 Resend 要求，第 4 条 DMARC 是我们自己加的加固项。

**三个反直觉的点，务必记住**：

| 点 | 说明 |
|---|---|
| **没有 MX** | 新版不需要 `feedback-smtp.*.amazonses.com`。若按旧资料配了 MX，**必须删掉**——MX 与 CNAME 不能在同一主机名共存，会直接阻塞第 2、3 条 |
| **`rsend-` 少一个 e** | 返回路径主机是 `rsend-apne1.forge.rmta.net`，**不是** `resend-apne1`。而 DKIM 的 selector 偏偏是完整的 `resend._domainkey`。同一页面两种拼写，极易看错 |
| **`apne1` = 东京** | `rsend-apne1` 里的 `apne1` 就是 ap-northeast-1 的缩写，可据此确认区域选对了 |

> ⚠️ **本表只是字段说明，不能作为填写来源。** 2026-10-24 首次配置发生过两起真实事故：
> ① 把上表的占位符原样填入，得到指向不存在域名的 DKIM 记录；
> ② 因手工抄写，把 `rsend-` 写成 `resend-`，造出一条 CNAME 目标 NXDOMAIN 的废记录。
> **唯一正确做法：打开 Resend → Domains → 域名 → Records，逐条点复制按钮粘进 Cloudflare，一条都不要手打。**

## 2. 分步操作

### 阶段 A｜注册 Resend（约 5 分钟）

1. 打开 `https://resend.com`，点 **Sign Up**
2. 用**一个现在就能收信的邮箱**注册（QQ / 163 / Gmail 均可）。**不要用 `@hongxian.dev`**——那个域还没有 MX，收不到信
3. 收验证邮件 → 点确认链接
4. 选择 **Free 计划**，**不需要信用卡**
5. 免费额度：**100 封/天，3000 封/月**。发布许可验证码每人 1 封，够用很久

### 阶段 B｜添加域名（约 5 分钟）

1. 左侧导航 → **Domains** → **Add Domain**
2. **Domain** 填：`mail.hongxian.dev`
   - ⚠️ 是子域，不是根域。用子域发信是送达率最佳实践，也隔离主域声誉
3. **Region** 选：**ap-northeast-1（东京）**
   - 收件人主要在国内，东京最近。若下拉里没有东京，选 `us-east-1`
   - **这个选择会体现在返回路径主机名里**（东京是 `rsend-apne1.forge.rmta.net`），选错要删域重建
4. **Custom Return-Path**：保持默认 `send`，不要改
5. **Receiving（收信）**：**不要开启**。我们只发不收
6. 提交后进入域名详情页 → **Records** 标签 → 这里应该有 **3 条记录**（1 条 DKIM TXT + 2 条 SPF CNAME），**没有 MX**

### 阶段 C｜在 Cloudflare 添加记录（约 10 分钟，最容易出错的一段）

**最优路径：先点 Resend 页面右上角的「Auto configure」**（图标是橙色云朵，说明 Resend 认出了 DNS 托管在 Cloudflare）。走 Domain Connect 授权后会自动写入全部记录，不用手抄。**只有自动配置失败时才手动。**

手动路径如下。先看一条**前置清理**：

> ⚠️ **若 `send.mail` 上已经有 MX 或 TXT 记录，必须先删除。** CNAME 不能与任何其他记录在同一主机名共存，Cloudflare 会直接拒绝，报错码 `81053`（"An A, AAAA, or CNAME record with that host already exists"）。这是旧版资料留下的坑。

1. 登录 Cloudflare → 选 `hongxian.dev` → 左侧 **DNS** → **Records**
2. **逐条点 Add record**，**每条都用 Resend 页面上的复制按钮粘，不要手打**

**记录 1（TXT / DKIM）**
- Type: `TXT`
- Name: `resend._domainkey.mail`（注意这里是完整的 `resend`，8 个字母）
- Content: `p=MIGf...IDAQAB`（约 218 字符的长公钥，**必须完整**）
- TTL: `Auto`
- ⚠️ 粘贴时**不要手动加引号**，Cloudflare 会自己处理。判据：值应以 `p=` 开头、以 `IDAQAB` 结尾

**记录 2（CNAME / SPF 返回路径）**
- Type: `CNAME`
- Name: `rsend.mail`（**这里是 `rsend`，少一个 e**）
- Target: `rsend-apne1.forge.rmta.net`
- Proxy status: **必须灰云 DNS only**

**记录 3（CNAME / SPF 发送路径）**
- Type: `CNAME`
- Name: `send.mail`
- Target: `send.forge.rmta.net`
- Proxy status: **必须灰云 DNS only**

**记录 4（TXT / DMARC，加在根域）**
- Type: `TXT`
- Name: `_dmarc`（**不是** `_dmarc.mail`）
- Content: `v=DMARC1; p=none; rua=mailto:<你的真实邮箱>; pct=100`
- TTL: `Auto`
- ⚠️ `rua=` 后面**不要写尖括号**，直接写地址：`rua=mailto:name@example.com`

> **为什么 DMARC 放根域**：一条根域 DMARC 覆盖所有子域（含 `mail.`）。放在 `_dmarc.mail` 只覆盖那一个子域，日后加别的子域要重复配。
> **为什么先 `p=none`**：观察期用。`p=reject` 一旦某天配置漂移，你自己的正常邮件会被对方直接拒收。**观察两周无异常再升级到 `quarantine`，再两周到 `reject`。**

### 阶段 D｜验证（15 分钟 – 72 小时）

1. 回 Resend 域名详情页 → 点 **Verify DNS Records**（或点 **Restart verification**）
2. 正常 **15 分钟内**全绿；DNS 全球传播最慢 72 小时
3. 自己先查一遍（PowerShell 或 CMD 均可）：

```
nslookup -type=CNAME rsend.mail.hongxian.dev
nslookup -type=CNAME send.mail.hongxian.dev
nslookup -type=TXT resend._domainkey.mail.hongxian.dev
nslookup -type=TXT _dmarc.hongxian.dev
```

**再加一条更硬的判据**——CNAME 的目标必须真实存在：

```
nslookup -type=TXT rsend-apne1.forge.rmta.net
```

应返回 `v=spf1 include:amazonses.com ~all`。**如果返回 NXDOMAIN，说明 `rsend-` 的 e 写多了，那条 CNAME 是废的。**nslookup -type=CNAME <hash1>._domainkey.mail.hongxian.dev
```

拿到的是 Resend 页面上的**同样值**才算对。

### 阶段 E｜建 API Key（2 分钟）

1. 域名验证通过后再建——这样能把 Key 直接限定在这个域
2. 左侧 **API Keys** → **Create API Key**
3. Name：`hongxian-publish-otp`
4. Permission：**Sending access**（**不要选 Full access**）
5. Domain：选 `mail.hongxian.dev`
6. **Key 只显示一次**，形如 `re_xxxxxxxx`
   - 立刻存进密码管理器
   - **不要贴到任何对话里、不要写进仓库任何文件、不要写进 `.env` 之外的地方**
   - 参考教训：此前 GitHub PAT 曾因贴进对话而泄露

### 阶段 F｜发测试信（5 分钟）

1. Resend 域名详情页通常有 **Send Test Email**；没有就走 API 或 Emails 页面
2. **From**：`noreply@mail.hongxian.dev`
3. **To**：分别发到 **QQ 邮箱**和 **Gmail** 各一封
4. 收到后打开邮件原文，确认三个头：

| 头 | 期望值 |
|---|---|
| `Authentication-Results` | `spf=pass` / `dkim=pass` / `dmarc=pass` |
| `Return-Path` | 以 `send.mail.hongxian.dev` 或 `rsend.mail.hongxian.dev` 结尾 |
| `From` | `noreply@mail.hongxian.dev`，**不应出现 `via resend.com`** |

5. 同时记录：进了收件箱还是垃圾箱。**这就是真实到达率的第一次实测**

## 3. 九个坑（按发生概率排序，前五条均已实际发生）

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| **0** | **手打而不是复制**（2026-10-24 已发生） | 把 `rsend-` 写成 `resend-`，CNAME 目标 NXDOMAIN，SPF 永远验证不过 | 一律用 Resend 的复制按钮。**判据：`nslookup -type=TXT rsend-apne1.forge.rmta.net` 必须返回 SPF 串，NXDOMAIN 就是拼错了** |
| **0b** | **把手册占位符当值填**（2026-10-24 已发生） | DKIM 值形如 `<hash>.dkim.amazonses.com`，目标不存在 | 删掉重加，值只能来自 Resend 页面 |
| **0c** | **DMARC 的 rua 带尖括号**（2026-10-24 已发生） | `rua=mailto:<name@example.com>`，报告全部丢弃 | 去掉 `<>`：`rua=mailto:name@example.com` |
| 1 | **`send.mail` 上残留 MX/TXT** | Cloudflare 拒绝创建 CNAME，报 `81053` | 先删同名的 MX/TXT/A/AAAA，CNAME 必须独占主机名 |
| 2 | CNAME 开了橙云 | Resend 一直 `pending` | 改成灰云 DNS only，等 1 分钟再 Restart verification |
| 3 | Name 填了全名 | 变成 `send.mail.hongxian.dev.hongxian.dev` | Name 只填相对部分 `send.mail`，Cloudflare 自动补后缀 |
| 4 | DKIM 值被截断或手加引号 | 状态 pending，值不以 `IDAQAB` 结尾 | 完整复制；判据：长度约 218 字符、以 `p=` 开头 `IDAQAB` 结尾 |
| 5 | 用 `@hongxian.dev` 地址注册或做 rua | 收不到验证信 / 报告全丢 | 一律用真实可收信的第三方邮箱 |
| **5b** | **Email Routing 权限只勾了 `Rules`**（2026-10-24 已发生，准备收信时） | 能列/能改转发规则，但看不了启用状态、加不了目标地址，全部返回 `10000 Authentication error` | 见 §8.4：`Email Routing`、`Rules`、`Addresses` 是**三个**独立权限组；本项目实测 `Zone → Email Routing` 在面板中**不可选**，用 DNS Edit 逐条写 MX/SPF 等价替代，**不构成阻塞**（§8.4.1） |
| **5c** | 把 Email Routing 的目标地址当成「填了就行」 | 规则建好也不转发，邮件静默丢弃 | 目标地址必须去收件箱点 Cloudflare 发来的验证信；未 `verified` 的地址不能作为 destination |

## 7. 首次配置复盘（2026-10-24）

这一节记录真实发生过的事，供以后接手的人对照——**配置文档最容易出错的地方不是技术，是信息源**。

### 7.3 两条方法论教训

1. **写配置文档不能基于搜索引擎结果。** v1.0 依据网上资料写成 AWS SES 形态（1 MX + 1 TXT + 3 DKIM CNAME），实际控制台早已换成 `forge.rmta.net` 形态（1 TXT + 2 CNAME，无 MX）。差异导致按文档操作的人必然失败。**要写操作文档，先看真实控制台截图。**

2. **DNS 是唯一可靠的裁判。** 截图会看错、文案会过时、记忆会混淆，但 `nslookup` 返回 NXDOMAIN 就是不存在。判断任何「这条记录对不对」，都去查它指向的目标能不能解析。

## 8. 收信通道：Cloudflare Email Routing（`hello@hongxian.dev`）

> **状态：未完成** —— 2026-10-24 21:10 实测卡在 Token 权限粒度（见 §8.4）。改权限后助手可全自动跑完，预计 3 分钟 + 等验证信。

### 8.1 为什么需要收信

产品对外必须有一个**得体、可持续、不暴露私生活**的联系地址。隐私声明 §10、境内站「关于」页、GitHub 组织主页、协议规范的联系方式，都要留一封能收到的信箱。用 `sunchaoxy@gmail.com` 会把个人邮箱写进宪法级文档并被永久抓取（且该地址已在 DMARC 里出现过一次，不宜再扩散）。`hello@hongxian.dev` 是唯一合适的对外身份，实际只是转发到 Gmail，不需要维护真实信箱。

### 8.2 为什么与 Resend 不冲突（关键，先说清再动手）

| 通道 | 作用域 | 占用的记录 |
|---|---|---|
| Resend（发信） | `mail.hongxian.dev` **子域** | `resend._domainkey.mail` TXT、`rsend.mail` CNAME、`send.mail` CNAME |
| Email Routing（收信） | `hongxian.dev` **根域** | 3 条根域 MX + 1 条根域 SPF TXT |

两者作用域是**父子域关系、互不覆盖**：根域写 MX 不会碰到 `mail.` 子域上的任何记录，反之亦然。所以「发信用 Resend、收信用 Cloudflare」可以长期共存，不需要二选一。**实测前提：根域当前 MX = 0 条、TXT = 0 条（无 SPF），是一张白纸，无清理动作。**

### 8.3 实际写入的 4 条记录（2026-10-24 21:08 写入并已全球生效）

| 类型 | Name | Content | 优先级 | 状态 |
|---|---|---|---|---|
| MX | `@`（根域） | `route1.mx.cloudflare.net` | 26 | ✅ 已写入 |
| MX | `@` | `route2.mx.cloudflare.net` | 16 | ✅ 已写入 |
| MX | `@` | `route3.mx.cloudflare.net` | 6 | ✅ 已写入 |
| TXT | `@` | `v=spf1 include:_spf.mx.cloudflare.net ~all` | — | ✅ 已写入 |

生效验证（21:09，`Resolve-DnsName -Server 1.1.1.1`）：三条 MX 全部返回、SPF 返回完整串。

> 根域 SPF 出现后，**DMARC 不受影响**（DMARC 是独立的 `_dmarc` TXT）。唯一副作用：将来若要从根域直接发信（如 `noreply@hongxian.dev`），需把发信商的 include 合并进这条 SPF，**不能并列两条 SPF**。当前发信走 `mail.` 子域，其 SPF 由 CNAME 指向 `rsend-apne1.forge.rmta.net` 自带的 SPF，与根域这条互不干扰 —— 21:08 实测仍能 `delivered`。

### 8.4 权限粒度：`Email Routing`、`Rules`、`Addresses` 是三个东西（2026-10-24 实际踩到）

一个 API Token 的 Email Routing 相关权限被 Cloudflare 拆成**三个独立权限组**，名字只差一两个词，照名字猜必错：

| 端点 | 用途 | 实测结果（Token 只含 Rules 权限时） |
|---|---|---|
| `GET /zones/{id}/email/routing/rules` | 列转发规则 | ✅ 200，能看到一条默认 `drop` 规则 |
| `GET /zones/{id}/email/routing` | 读启用状态 | ❌ `10000 Authentication error` |
| `GET /zones/{id}/email/routing/dns` | 读 MX/SPF 托管状态 | ❌ `10000` |
| `PUT /zones/{id}/email/routing/dns` | **启用**并写 MX/SPF | ❌ `10000` |
| `GET` / `POST /accounts/{acc}/email/routing/addresses` | 目标地址列表 / 新增 | ❌ `10000` |
| `POST /zones/{id}/dns_records` | 普通 DNS 写（对照组） | ✅ 200，证明 DNS 权限本身没问题 |

**结论：能列规则 ≠ 能启用。** 需要的权限：

| 位置 | 权限组 | 级别 | 用途 | 本项目实况 |
|---|---|---|---|---|
| Zone | `Email Routing` | Edit | 官方「启用」开关 + 写 MX/SPF | ❌ 面板里**不存在该可选项**（2026-10-24 实测） |
| Zone | `Email Routing Rules` | Edit | 建 `hello@` → 转发规则 | ✅ 有 |
| Account | `Email Routing Addresses` | Edit | 新增并验证目标地址 | ✅ 有 |
| Zone | `DNS` | Edit | 逐条写 MX/SPF | ✅ 有（发信配置时已具备） |

#### 8.4.1 关键结论：第三项缺失**不构成阻塞**

`PUT /zones/{id}/email/routing/dns` 这个「启用」端点实际只做两件事：**写那 4 条记录** + **置一个启用标志**。前者可以用 `POST /zones/{id}/dns_records`（DNS Edit）逐条等价完成，后者在 MX 已指向 `route*.mx.cloudflare.net` 之后由 Cloudflare 入站网关自动接管 —— 因为判断「这封信该不该由 Email Routing 处理」的依据就是**根域 MX 指向**，而不是面板上的一个布尔位。

因此把「必须拿到 `Zone → Email Routing → Edit`」当成前置条件是**过度假设**。正确路径是：**有 DNS Edit 就自己写 MX/SPF，然后建规则，再用真实邮件验证**（验证方法见 §8.5，这一步不能省）。

> 若将来面板里出现了 `Email Routing` 这个权限组且想走官方开关，仍以「面板能点、端点能通」为准，不要照文档猜。

**方法论教训（与 §7.3 同源）**：Cloudflare 把「一个功能」呈现为一个名字，底下却是三个权限组；「已授权」必须以**端点实测**为判据，不能以「我勾过了」为判据。**同样地，「缺一个权限」也不等于「做不到」——先分清那个权限到底在做什么，再找等价路径。**

**为什么第 6 步不能省（本环节最重要的一条）**：

> **`delivered` ≠ 转发成功。** Resend 的 `delivered` 只表示 Cloudflare 的 MX 在 **SMTP 层**回了 250（收下这封信）。若该域的路由未生效，Cloudflare 的行为是「**先收下、后静默丢弃**」——发件方拿到成功回执，收件方什么也收不到，全程没有任何退信。这就是本环节最危险的**假成功**。

判据必须两条都过，本次均通过：
1. **正向**：Gmail 里真的出现了那封题为「[红线] 收信通道闭环测试 v1」的信 ✅
2. **反向**：发往 `nobody-9f3a@hongxian.dev` 被 **hard bounce** ✅ —— 比「收不到」更强的证据：CF 在 SMTP 阶段就拒了，说明没有任何 catch-all 兜底。

**第 8 步的补充说明**：`rua` 改完后，DMARC 聚合报告会先投到 Cloudflare、再转发到 Gmail，比原来多一跳。**若两周内发现某天的报告缺失，把 `rua` 临时改回双地址**（`mailto:hello@hongxian.dev,mailto:sunchaoxy@gmail.com`）排查，不要直接放弃域名邮箱。

### 8.6 这个环节的坑

| # | 坑 | 说明 |
|---|---|---|
| 1 | 目标地址未验证就建规则 | 规则能建成但邮件静默丢弃，**无任何报错**。这是最危险的失败模式：以为通了，实际每封都掉 |
| 2 | 开 catch-all | 会让 `随便什么@hongxian.dev` 全部落到 Gmail，招垃圾邮件并暴露「域名有人住」；只开 `hello@` 单地址 |
| 3 | 根域 MX 被覆盖 | 将来若接入别的收信服务，MX 是**互斥**的，不能并存；Email Routing 一开，根域收信权就归 Cloudflare |
| 4 | 先改 DMARC 再验收 | 报告地址指向一个还没通的信箱，等于主动丢证据 |
| **5** | **把发件方的 `delivered` 当转发成功**（本次差点误判） | SMTP 250 只代表 MX 收下。Email Routing 未生效时是「收下 + 静默丢弃」，**零退信**。见 §8.5 |
| **6** | 把「缺 Zone Email Routing 权限」当成硬阻塞 | 该端点只是写 MX/SPF + 置标志，DNS Edit 即可等价完成。先问「这个权限在做什么」，再决定是否真需要它。见 §8.4.1 |
