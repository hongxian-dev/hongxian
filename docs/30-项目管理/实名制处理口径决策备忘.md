> **一句话**：**密钥仍是唯一身份；邮箱验证只是「贴卡许可证」，不是账号，也不是实名认证。**

## 1. 为什么这条必须最先定

它是关键路径的起点，不是因为排期，而是因为**它不定，四件事都无法判定**：

| 悬空的事 | 为什么悬空 |
|---|---|
| 隐私声明 | 不知道收不收手机号，就不知道写什么 |
| 三条防护 | 「明示不实名」这句在方案 B 下要改成「明示披露范围」 |
| 广场实现 | 贴卡要不要验证，直接决定端点和数据结构 |
| 闭环验收 D 组 | TC 关于广场的预期结果无法写 |

## 2. 法律依据（已核准，勿再凭印象引用）

| 依据 | 内容 | 对我们的意义 |
|---|---|---|
| 《网络安全法》**第 26 条**（2025 修正后条号，**旧版第 24 条已作废**） | 网络运营者为用户办理网络接入、域名注册、固定/移动电话入网手续，或**提供信息发布、即时通讯等服务**时，应当要求用户提供真实身份信息；不提供的不得提供服务 | **列举式**义务，只覆盖五类服务；我们要落进「信息发布」才触发 |
| 《网络安全法》**第 61 条** | 违反第 26 条：责令改正；拒不改正或情节严重，处 **5 万–50 万**罚款，可责令暂停业务、停业整顿、**关闭网站**；直接责任人 1 万–10 万 | 罚则针对「境内可执法的运营者」 |
| 《互联网用户账号信息管理规定》**第 9 条** | 为信息发布、即时通讯等提供账号注册的，应做基于**移动电话号码**、身份证件号码或统一社会信用代码等方式的真实身份信息认证 | **手机号即为法定认证方式**，不必收身份证 |
| 同上 **第 2 条** | 适用于用户在「**中华人民共和国境内的**互联网信息服务提供者」注册使用账号 | 我方服务在首尔，**不在该规定射程内**；但《网络安全法》本身未限定「境内」，故不能据此免责 |

**必须诚实看待的一条**：境外服务器不等于不受中国法约束，但执法手段主要是**阻断访问**，而非对中国籍个人罚款。也就是说：

> 不实名的现实代价，是「国内用户全部连不上」，不是「创始人被罚 50 万」。

这个代价依然足够致命——它等于国内线归零。所以不能用「反正管不到我」当决策依据。

## 3. 关键判断：风险不均质，命门只有一处

| 环节 | 性质 | 实名义务 |
|---|---|---|
| 建画像 / 本地比对 / 出报告 | **本机计算**，不构成对外服务 | ❌ 不触发 |
| 信箱投递（点对点加密） | 可争「技术服务」，无公开内容池 | 🟡 争议区（依赖律师意见） |
| **广场贴卡（公开可见列表）** | **信息发布**，几乎无法抗辩 | 🔴 **明确触发** |
| 代访（AI 代理问答） | 是服务，但不属信息发布 | ❌ 不触发 |

> **结论：实名的真实触发点是「把卡贴到广场」这一个动作，不是「用月老」。**
> 信箱是邮局，广场是公告墙——只有公告墙要求发布者实名。

## 4. 决策：方案 B —— 发布侧轻实名

**只在贴卡上广场时要求邮箱验证。其他一切环节不要求。**

### 4.1 四条硬约束（不可让步，写进验收）

| # | 约束 | 具体做法 | 保住了什么 |
|---|---|---|---|
| 1 | **不进登录链路** | 邮箱不能登录、不能找回账号、不能替代恢复短语 | 密钥即身份 |
| 2 | **不存明文** | 只存 `HMAC-SHA256(标准化邮箱, 服务端盐)`；一个哈希只对应一个 `owner_key_id` | 零知识不破 |
| 3 | **不对外展示** | 任何界面、任何信封、任何报告中都不出现 | 前台匿名 |
| 4 | **只在贴卡时要求** | 安装、建画像、收卡、比对、深聊、L2/L3 全都不要求 | 用户流失压到最低 |

### 4.2 已接受的代价（不粉饰）

| 代价 | 处理方式 |
|---|---|
| 品牌叙事要改 | 早期说过「不收集任何身份信息」→ 改为「**我们不验证你是谁，只确认这个邮箱能收到信**」；官网 Q8、信任清单、协议、隐私声明四处同步 |
| PIPL 义务上升 | 邮箱哈希仍属个人信息：单独同意、最小化、可删除、明示保存期，全部落进隐私声明 |
| ~~海外用户无国内号~~ | **B-mail 反而消除了这个限制**——Gmail 也能收，开源项目的海外用户不再被挡在广场外 |
| 一邮箱一密钥 | 一个邮箱只能绑一个密钥（防女巫、防一人刷满广场）；换密钥需解绑重绑 |
| 邮件服务商在境外 | 邮箱地址会经该公司服务器出境（**本项目用 Resend，美国公司，发信节点 AWS 东京**），隐私声明已明写 |
| 服务端在验证瞬间可见明文邮箱 | 只能做到「内存中发信与比对后立即丢弃、不落日志」；此点必须写进隐私声明，不许含糊 |
| 成本 | 免费额度内 0 元（Resend 100 封/天，够冷启动） |
| 到达率不是 100% | QQ / 163 约 70–85%，必须给「查垃圾箱 / 换 Gmail」提示，并允许重发 |
| **法律强度不足** | 邮箱**不构成**第 26 条「真实身份信息认证」。这一条是本方案最真实的弱点，只能靠「三条防护 + 举报即断 + 明示」缓解，不能消除 |

### 4.3 为什么不是方案 A / C

| 方案 | 否决理由 |
|---|---|
| A 全面不实名 | 广场那一环站不住。域名被墙 = 国内线归零，与「做十年」的定位不兼容 |
| C 境外限定邀请制 | 邀请制不减免法律义务，只降低被注意的概率。靠不被注意活着，不是产品设计 |
| 「用户自证已实名」勾选 | 法律上无效，等于没做，还额外制造「明知故犯」的证据，比不做更糟 |

三条可行路径：

| 路径 | 载体 | 资质门槛 | 法律强度 | 成本 | 可落地时间 |
|---|---|---|---|---|---|
| **B-mail（推荐先做）** | 邮箱 OTP（国际邮件服务，个人可开通） | 无 | **中低**：可追溯、可防女巫，但**不构成第 26 条法定「真实身份信息认证」** | 免费额度内 ≈ 0 | 今天 |
| **B-sms（个体户）** | 手机号 OTP | 需个体工商户（可开短信、可办企业备案、可上小程序） | **中高**：手机号是法定认证方式 | 注册几百 + 记账报税 2000–3000/年 | 1–2 周 |
| **B-sms（借他用资质）** | 手机号 OTP | 借他人公司资质 | 中高 | 人情 + 责任转移 | 不可控 |
| B 延后 | 无 | 无 | — | 0 | 广场不开，闭环断裂 |

**本文档后续规格以「载体可替换」方式书写**：把 `phone_hmac` 视作 `carrier_hmac`，端点名不变。走 B-mail 时该字段存 `HMAC(标准化邮箱)`，文案把「手机号」改为「邮箱」，隐私声明同步。

**走过的弯路要记住**：先按「手机号」设计，落地时才发现资质门槛——所以任何涉及「需要第三方资质」的设计，都必须在方案阶段先核资质，不能等开发。

### 5.1 数据模型

```
publish_credentials
  carrier_hmac    TEXT  PRIMARY KEY   -- HMAC-SHA256(标准化载体值, SERVER_SALT)
                                      -- 手机号时 = 11 位号码；邮箱时 = 小写去空格的地址
  owner_key_id    TEXT  UNIQUE NOT NULL
  verified_at     INTEGER NOT NULL
  last_otp_at     INTEGER             -- 限速用
  revoked_at      INTEGER             -- 解绑时间，null 表示有效
```

- `SERVER_SALT` 从环境变量读，**不入代码、不入库**；轮换盐等于全部解绑，故盐有长期稳定性要求
- 邮箱标准化：转小写、去首尾空格；必须含 `@` 且域名有 MX 记录；**不做 `+` 别名展开**（否则一个 Gmail 能绑无限身份，防女巫形同虚设）
- 一次性邮箱域名（mailinator / temp-mail 等）建黑名单拒绝——防刷，但会误伤少数真实用户，故只拦高频名单，不做大而全
- 该表**不与其他任何表关联**，不留 IP、不留 UA、不留时间戳以外的元数据

### 5.2 端点（新增两个，改动一个）

| 端点 | 作用 | 限速 |
|---|---|---|
| `POST /v2/publish/otp` | 发验证码。入参 `{carrier, owner_key_id}` | 每载体 1 次/分钟、5 次/天；每 IP 10 次/小时 |
| `POST /v2/publish/verify` | 校验验证码 → 写入 `publish_credentials` | 每载体连续错误 5 次锁 1 小时 |
| `POST /v2/plaza`（改动） | 贴卡前校验该 `owner_key_id` 存在有效 `publish_credentials`，否则 **403 `publish_requires_verification`** | 沿用现有 |

**验证码规则**：6 位数字，有效期 5 分钟，一次性；存储只存哈希；错误次数与过期均不区分提示（防枚举）。

**重要**：`/v2/publish/otp` 与 `/verify` 是**平台首次接收明文个人信息**的入口。三环制里它属于「身份凭据环」——单独成一个环，**永不与内容环、聚合环、行为分析环做任何 join**。宪法数据三环制需相应增补为四环，见 §8。

### 5.3 客户端交互（这里是真实难点）

MCP 客户端里不能直接收短信、也不该让用户在终端输手机号。**流程必须走浏览器**：

```
月老：要把这张卡贴到广场吗？广场是公开列表——为了防止一个人刷满广场，
      也为了出事时有一个处置入口，贴卡前要确认一个邮箱能收到信。
      这不是注册，不收密码，也不验证你是谁。
      ↓ 用户同意
月老：请在你的浏览器打开：https://hongxian.dev/publish-verify/?n=<nonce>&k=<opaque_id>
      ↓ 用户在网页填邮箱 → 收信 → 填验证码
网页：显示 6 位「发布许可码」
      ↓ 用户回填给月老
月老调用 verify（携带许可码 + owner_key_id）→ 成功 → 继续贴卡
```

- `nonce` 一次性、5 分钟有效、绑定 `owner_key_id`，防止替他人验证
- 网页需明确写：这一步只验证号码可达，不验证你是谁
- **用户拒绝时**：仍可导出卡、仍可点对点投递、仍可收卡与比对——只是不能上广场。月老必须把这句话说出来
- 降级：短信通道不可用时，网页提示「稍后重试」，不允许静默失败

### 5.4 解绑与注销

- 用户可主动解绑（失去贴卡能力，历史卡片保留，不追溯下架）
- `wipe` 注销本地身份时，服务端对应 `publish_credentials` 一并删除（跟随现有注销级联）
- 号码哈希保留至解绑/注销为止，不设自动过期（否则长期不活跃用户会突然被要求重新验证）

## 6. 文案改写（三处，均为定稿，可直接落地）

### 6.1 官网 FAQ Q8（原「不用手机号，怎么证明"我是我"」）

> **Q8｜要不要手机号？我的身份怎么证明？**
> **不用手机号，密钥即身份。** 注册 = 在你设备上生成一对密钥，平台只保存公钥档案，没有密码。
> 唯一凭证是 **24 词恢复短语**——抄在纸上，别拍照存云盘。丢了它等于丢了这个身份。
> **唯一例外**：把卡贴到「红线广场」（一个公开可见的列表）时，要确认一个邮箱能收到信。这**不是实名认证，我们也不假装是**——它只做两件事：防止一个人刷满广场、留一个出事时的处置入口。邮箱不能登录、不能找回、不展示，只存加盐哈希。
> **不收卡、只和认识的人换卡，全程不需要邮箱。**

### 6.2 信任清单（五步）新增一条

> **⑤ 邮箱只做一件事**：贴广场前确认这个邮箱能收信，存加盐哈希。它不能登录、不能找回、不出现在任何卡里。**我们不验证你是谁——这一层目前做不到，所以我们不声称做到了。**

### 6.3 协议规范 v1.3 增补条款

> §X 发布许可（publish credential）
> 广场发布需携带由平台签发的发布许可。客户端 MUST NOT 在本许可之外在任何信封中携带邮箱地址或邮箱哈希。发布许可与身份密钥分离：许可失效不影响身份、不影响信箱收发。
> 发布许可**不构成身份认证**，协议层面不得据此推断用户真实身份、不得用于排序或推荐。

## 7. 隐私声明要点（完整版见 `docs/00-定位与PRD/隐私声明.md`）

必须写清的六句话，一句都不能少：

1. 平台对内容的了解上限是「密文」——改代码也解不开
2. 平台知道「某个假名公钥做了什么」，不知道「这个人是谁」
3. **唯一例外**：贴广场的邮箱，平台能知道「某个假名对应某个邮箱哈希」
4. 明文邮箱在验证瞬间存在于服务端内存，发信与比对后立即丢弃，**不写日志、不入库明文**
5. 数据存在首尔（境外），构成数据出境；零知识下出境的是密文
6. 你可以随时导出、删除、退出行为分析；注销即级联清零

## 8. 对宪法「数据三环制」的增补

原三环：内容环（零知识）/ 聚合环（匿名指标）/ 行为分析环（假名绑密钥）。

**新增第四环：身份凭据环**

| 环 | 存什么 | 谁能看 | 隔离要求 |
|---|---|---|---|
| 内容环 | 三层加密 payload | 无人（平台无密钥） | 零知识 |
| 聚合环 | 只有总和 | 公开 | 无个体 ID |
| 行为分析环 | 频次/路径/设备 + 假名 ID | 仅运营者 | 禁关联真实身份 |
| **身份凭据环（新）** | 号码哈希 ↔ 假名公钥 | 仅运营者，且仅在执法配合场景 | **永不与其他三环 join**；不用于排序、不用于推荐、不用于画像 |

宪法 §4 需相应修订（**待下一版定位声明一并更新，本文档为增补依据**）。

## 9. 律师三问（按第 26 条重新校准）

问法要具体到能拿到可执行结论：

1. 加密信箱（平台无解密能力、无公开内容池）是否构成《网络安全法》**第 26 条**所指「即时通讯服务」？**广场的卡片列表是否构成「信息发布」**？若仅广场构成，则「发布侧实名、接收侧不实名」的分割是否足以履行义务？
2. 运营主体为中国籍个人、服务器在境外（首尔）、服务对象主要为境内用户时，第 26 条与第 61 条的管辖与执法路径如何？实务中是否以阻断访问为主？
3. **邮箱验证能否满足第 26 条「真实身份信息」要求**？若不满足（我们的预判是不满足），则：① 广场是否构成「信息发布」从而触发该义务；② 若不构成，邮箱仅作防滥用措施是否足够；③ 若构成，是否必须上手机号（即必须先有经营主体）。哈希存储是否影响「可提供协助」义务（公安依法调取时，能否凭哈希定位到邮箱）？

## 11. 回滚条件（什么情况下退回方案 A）

出现任意一条，本决策需重新评估：

1. 律师书面意见明确「信箱+广场均不构成信息发布或即时通讯」→ 可退回方案 A，删掉整个发布许可模块
2. 邮件到达率持续低于 60%（QQ/163 实测），导致正常用户无法贴卡 → 换通道，或改申请制广场
3. 用户因手机号验证流失超过 50%（首月实测）→ 说明成本高于合规收益，改「广场申请制 + 不公开可见」
4. 出现号码哈希库泄露风险事件 → 立即停止收集，改纯邀请制

## 12. 未采纳但保留的思路

**广场申请制（不公开可见）**：用户不浏览卡片，而是提交自身条件，系统返回「有 N 位符合条件的人」，双方同意后才互相可见。

- 优点：不构成「公开信息发布」，实名义务大幅弱化；且更符合双盲设计
- 未采纳原因：它把「发现」变成了「被系统告知」，与「不匹配、不推荐」四军规的边界极难把握，容易被读成推荐
- 保留为**方案 B 失败后的第一备选**，需先解决四军规的边界表述
