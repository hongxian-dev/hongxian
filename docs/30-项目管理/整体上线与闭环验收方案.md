## 0. 口径：一个产品，四件套，一次上线

### 0.1 产品定义

红线是**一个完整产品**，由四件不可或缺的部分组成，缺任何一件都不构成完整闭环：

| 件 | 是什么 | 缺了会怎样 |
|---|---|---|
| **月老 Skill（客户端）** | 用户侧的 AI Agent 能力，建画像、出卡、比对、出报告、代访、见面 | 没有产品，只剩一堆协议文档 |
| **红线平台服务** | 月老与月老之间的通信基础设施（信箱 + 广场 + 举报 + 匿名聚合） | 两个陌生人无法相遇，只能熟人手动递卡，产品扩不开 |
| **红线协议** | 卡结构与信封格式的公开规范 | 第三方月老无法接入，项目不是"基础设施"只是一款软件 |
| **产品介绍网站** | 官网（境外）+ 境内镜像笔记站 | 用户找不到入口、装不上、不信你 |

### 0.2 版本命名规则（即日生效）

| 对象 | 编号方式 | 现行值 |
|---|---|---|
| **产品版本** | 只有一条线，首发即 **1.0**，之后 1.1 / 1.2 | **1.0（未发布）** |
| 红线协议 | 独立编号，按协议演进 | v1.2 |
| 匹配卡 Schema | 独立编号 | 文档 v0.3 / 机器可读 v0.5 |
| HTTP 端点 | 路径内的 `/v2/` 是 **API 版本**，与产品版本无关 | — |

**今后任何场合不再用"V1 / V2 / V3"指代产品阶段。** 旧文档里的 v1/v2/v3 字样，凡指产品分期的，一律视为历史表述，以本文为准。

### 0.3 为什么放弃分期（记录理由，避免反复）

分期发布曾经的作用是"把能做的和卡住的隔开"，但它有一个致命副作用：

> **它允许在"产品还不完整"的状态下宣布发布。**

阶段性的发布物是这样的：用户装上 Skill 后，只能找熟人手动换卡——**这不是产品，是演示**。真实用户装上以后会问"然后呢"，而答案是"你自己找人"。分期发布的代价不是慢，是**第一批用户的信任被浪费掉**，而冷启动阶段的信任只有一次。

所以合并为一个版本不是节奏选择，是**产品成立的必然要求**。

## 1. "上线"的定义（Go 的唯一含义）

> **上线 = 一个陌生人，从看到官网开始，到与另一个陌生人走到线下见面，全程无需项目作者参与、无需人工介入、无需熟人介绍。**

这句话拆成四个可判定的条件：

| # | 条件 | 判定方式 |
|---|---|---|
| 1 | 陌生人在自己的设备上能装好并跑起来 | 干净设备全流程（TC-01） |
| 2 | 两个互不相识的用户能通过平台互相发现 | 双账号广场闭环（TC-14） |
| 3 | 能一路走到交换联系方式（L3）并线下见面 | 三阶阶梯全链路（TC-19 / TC-20） |
| 4 | 上面三步不需要任何人工帮忙 | 执行者不得询问项目作者 |

**四条全满足才算上线。** 任何一条不满足，状态叫"未上线"，不叫"分阶段上线"。

## 3. 关键路径：谁在拖整体上线

整体上线后，**上线时间由最慢的那件事决定**。把依赖排出来：

```
实名制口径决定 ──┬─→ 隐私声明 ──→ 三条防护补齐 ──→ 上线合规基线
                │
                └─→（若需实名）实名层设计实现 ─────────┘
                                                      │
首尔服务器采购 ─→ 部署 + HTTPS + 域名解析 ────────────┤
                                                      ├─→ 闭环联调（33 场景）─→ 上线
npm 发布 ─→ 安装文档同步 ─────────────────────────────┤
                                                      │
多端点 / 首次提示 / 明示不实名 ───────────────────────┘
```

**三条最长的链，按耗时排序：**

| 顺位 | 链条 | 性质 | 为什么它最长 |
|---|---|---|---|
| 1 | **实名制口径 →（可能）实名层实现** | 决策 + 工程 | 若要实名，产品宪法要改，且零知识架构要重设计；若不要实名，需要能站得住的依据 + 三条防护 |
| 2 | **闭环联调 33 场景** | 工程 + 人 | 四件套第一次真正一起跑，问题会成堆出现，无法预估 |
| 3 | **npm 发布 + 安装简化** | 决策 + 小工程 | 一条命令装不上，前面全白做；不发布则用户必须装开发环境 |

**结论：整体上线的关键路径不再是代码，而是"实名制问题的处理口径"。** 这一条不定，隐私声明写不了、三条防护补不准、实名层不知要不要写——三条链全部悬空。

## 4. 闭环验收场景清单（33 个场景）

### 4.1 执行前提

| 项 | 要求 |
|---|---|
| 执行人 | **不参与开发的第二人**（开发者自测不算；这是唯一能暴露"我以为你会用"的方式） |
| 设备 | 至少两台干净设备（建议 Windows 一台 + macOS 一台），均未装过本项目 |
| 账号 | 两个全新密钥对（两个"真人"，互不认识） |

## 6. 上线后 30 天该盯什么

| 指标 | 定义 | 为什么是它 |
|---|---|---|
| **完成双向同意的姻缘线数** | 双方都点了"愿意继续"，且已交换 L2 | 这是"深度匹配真的发生过"的唯一证据，不是注册量 |
| L3 交换率 | 达成 L2 的线里，走到交换联系方式的占比 | 判断"匹配质量"而非"热度" |
| 闭环断点分布 | 33 个场景里用户实际卡在哪一步 | 决定下个迭代做什么，比任何需求评审都准 |
| 举报触发率 | 独立举报人数达阈值的卡占比 | 反诈与内容治理的健康度 |
| 安装成功率 | 到官网 → 装好 → 建立画像的转化 | 判断 npm 发布与文档是否够好 |

**明确不看**：注册量、对话轮次、停留时长、日活。这几个数字与"是否真的帮人找到人"无关，看多了会把产品带向"刷量"。

## 7. 风险

### 7.1 整体上线带来的新风险（分期时不存在）

| 风险 | 说明 | 应对 |
|---|---|---|
| **风险集中释放** | 四件套第一次一起跑，问题会叠加出现（客户端问题 vs 服务端问题难分辨） | 严格按 A→F 组顺序执行，前一组不通过不进下一组 |
| **无人可用作退路** | 分期时至少能发个客户端，现在没有"部分上线"这个选项 | 接受。半成品上线比晚上线更伤 |
| **关键路径取决于一个决策** | 实名制口径未定，三条链悬空 | **把它当唯一 P0**，其余全部并行 |
| **合规瑕疵直接归零** | 备案/实名/数据出境任一问题，会让整站下线而非某功能下线 | 见 5.3 内部红线 |

### 7.2 已有风险（仍有效）

| 风险 | 应对 |
|---|---|
| 备案二次被驳 | 境内站按「开源实战笔记」做，不带产品叙事；由验收脚本硬拦营销词 |
| 平台单点故障 | 每日备份到对象存储；用户恢复短语不能替代平台侧信箱备份 |
| 首发帖延后失窗口 | 与闭环验收并行准备，不占关键路径 |

### 7.3 法律意见该问的三问（若要咨询）

1. 加密信箱（平台无法解密、无公开内容池）是否构成《网络安全法》**第 26 条**（2025 年修正后条号，旧版为第 24 条）所指"即时通讯服务"？**广场的卡片列表是否构成"信息发布"**？若是，实名要求如何与零知识架构兼容？
2. 平台不核验用户身份、仅提供加密转发，用户间诈骗时的责任边界在哪？
3. 服务部署在境外（首尔）、面向境内用户，数据出境的合规义务具体到哪一步（告知同意是否足够）？
